# Spec M52 -- the standard library becomes installable, and the binary carries only the compiler's own source

Written against `minicompiler/mc` `main` at `c7b8cfc` (version constraints for `[deps]`), read-only
session except for the probes of § 1.3, 2026-09-08, on the Apple M4 / macOS 26.6.2 host
[`../comparison.md`](../comparison.md) measures. There is no `docs/plan.md` row to quote: this
milestone starts from the owner's direction, and [`../plan.md`](../plan.md)'s row is written from
this spec and not the other way round.

The owner's direction, verbatim (2026-09-08):

> M51 não violaria se fosse lib, não bundle, e mesmo os bundles podemos converter em libs que podem
> ser instaladas (caso não existam) no momento do build de uma aplicação. Dessa forma o binário do
> mc fica mais enxuto, portando somente o que é estritamente essencial e verdadeiramente dependência.

The one-paragraph version. The measurements move this milestone from "carve the libraries out into
packages" to something much smaller, and they do it twice. First, the size: applying the owner's own
rule per bundle row -- a row stays iff the compiler itself is built from it -- takes **41 of 101 rows
and 123 315 of 678 368 blob bytes** out, which is 10.0% of the binary (1 408 576 -> **1 268 276 B**,
measured by regenerating the blob and rebuilding, § 1.2) and **not one byte of `__text`**, because the
essential set *is* the compiler's own source and that is 82% of the blob. Second, the mechanism: the
road that serves a library name the blob no longer carries **already exists and needed no design at
all** -- resolution step 3, `<libs>/mc/v<version>/`, reached on a bundle miss
([`../reference/packages.md`](../reference/packages.md) § 2), which § 1.3 proves end to end on this
host: a thinned compiler refuses `#include <sys>`, `mc install --from-tree .` populates the tree in
0.28 s with no network, and the same compiler then builds a **taught float compiler** out of
`<mc/core>` + `<user_float>` whose object is **`cmp`-identical** to the one the unthinned compiler's
taught compiler writes. So M52 is not a packaging milestone: it is a one-predicate change in
`tools/bundle.mc`, two more roots in `dp_mc_load` so that the tree ships beside the binary and the
offline promise survives, one widened refusal, and the test and doc migration. **Zero `#include`
lines change anywhere** -- `<float>` is spelled `<float>` before and after -- which is what makes the
0.16.0 cut safe for the consumer. Publishing `float`, `i128`, `io` as registry packages of their own
stays priced and deferred (§ 9), for one measured reason: only ONE bare name per package survives (a
package's `lib`), so `<machine_arm64_float>` would have to become `<float/machine_arm64_float.mc>` in
every consumer, and the single-file CLI has no lock road at all.

## 0. What this stands on (read, not assumed)

* **The three resolution roads.** `lex_include_name` (`src/lex.mc:1041`) strips a trailing `.mc` and
  tries, in order: `lex_include_libs(name, 0)` -- the lock road, only when the name's first path
  component is a package `mc.lock` names and the including file may reach it (`:1046`);
  `lex_include_bundled(name, 0)` -- the blob (`:1048`, `lex_include_bundled` at `:971`, a no-op when
  `bopen_fn == 0`, `:713`); and `lex_include_libs(name, 1)` -- **the installed `mc` package**
  (`:1050`). Only then does it refuse. The two openers arrive as function pointers, `bopen_fn` from
  `lex_set_bundle` (`:715`) and `lopen_fn`/`lhint_fn` from `lex_set_libs` (`:745`), so the lexer
  depends on neither `src/bundle.mc` nor `src/deps.mc`.
* **Stage 1 is not gated on the flavour.** `libs_open` (`src/deps.mc:1313`) forwards any non-zero
  stage to `dp_mc_open` (`:1270`), which reads `<libs>/mc/v<mc_version()>/` with `bundle.list` at its
  root as the NAME<TAB>PATH map (`dp_mc_load`, `:1226`). Nothing there tests whether this binary has
  a blob; the comment says "a full binary answers every one of these names from its blob and never
  reaches this step", which is a statement about today's manifest, not a guard. **Only the hint is
  gated**: `lex_include_name:1060` asks `dep_include_hint` (`src/deps.mc:1300`) *only* when
  `bopen_fn == 0`.
* **Step 3 verifies nothing.** `dp_mc_load` reads `bundle.list` and `dp_mc_open` reads the named file
  through `lex_readable`; there is no hash, no manifest check, and a missing file simply falls
  through to the next road. `<libs>` is `--libs-dir DIR` when given, else `host_home()/.mc/libs`
  (`deps_libs_root`, `:1209`; `deps_set_libs_dir`, `:1219`), and `--libs-dir` is parsed by
  `mc build`, `mc pkg`, `mc install`, `mc upgrade` and `mc tool` -- **not** by the single-file CLI
  (`src/core_build.mc:54`, `src/core_pkg.mc:37-55`; no `opt_val(a, "--libs-dir")` in `src/cli.mc`).
* **`mc install` already installs the compiler's own package** (`src/install.mc`, M44 step 4):
  `mc install [VERSION] [--from-tree DIR]` resolves the `mc` row from the registry, or hashes and
  copies `mc.toml` + `[package].files` out of a checkout, and then `ins_bundle_list` (`:45`) copies
  `tools/bundle.list` to the root of the tree -- the file step 3 reads. The root `mc.toml` declares
  **105 files** (`grep -c '^    "' mc.toml`), which is every path of `tools/bundle.list` plus
  `src/bundle_data.mc`, `tools/bundle.list`, `src/mc_linux_x86_64.mc` and `src/user.mc`. So the
  libraries are **already** files of the `mc` package; nothing has to be moved for them to be
  installable.
* **`host_self_path()`** exists in all three host layers (`src/host_macos.mc:114`,
  `src/host_linux.mc:82`, `src/host_windows.mc:91`) and is read by `src/upgrade.mc:333` and
  `src/tool.mc:344/422`. It is `_NSGetExecutablePath` / `readlink /proc/self/exe` /
  `GetModuleFileNameA`, never `argv[0]`.
* **`mc build` never downloads**, and that is proved rather than asserted:
  [`../reference/packages.md`](../reference/packages.md) § 9, with `scripts/check-pkg.sh` running the
  whole suite under a `curl`, a `wget` and a `tar` on `PATH` that exit 97 if invoked.
  [`../determinism.md`](../determinism.md)'s rule is that one source gives one answer on every
  machine.
* **A taught compiler's modules are included in array order.** `drv_gen_compiler`
  (`src/driver.mc:505`) writes `#include <mc/host>`, then `[compiler].core` (or `<mc/core>` by
  default, `:528`), then one line per `[compiler].modules` entry through `drv_include` (`:479`),
  which emits a value starting with `<` **verbatim**. So `modules = ["<float/float.mc>", "<mine.tk>"]`
  already orders a library ahead of a language module with no new mechanism.
* **The blob's generator.** `make bundle` (`Makefile:140`) is `build/mc1 --exe tools/bundle.mc` then
  `build/bundle tools/bundle.list src/bundle_data.mc`. `tools/bundle.mc` writes names and file bytes
  and nothing else -- "no path, date or address reaches the blob" is its own comment, and
  [`M47-S5.md`](M47-S5.md) § 4.2 verified it.
* **The reserved names** are `mc`, `mc/...`, `deps` and `build` (`dep_reserved`, `src/deps.mc:106`).
  `float`, `io`, `sys`, `i128`, `f16` are **not** reserved: any account could register them today.
* **What `src/` actually includes from `lib/`.** Two files, measured with
  `grep -rn 'lib/' src/*.mc`: `../lib/prelude.mc` (16 files -- `backend_coff`, `backend_coff_exe`,
  `backend_elf`, `backend_elf_exe`, `backend_exe`, `driver`, `gen_resolve`, `limits`, `macho`,
  `objmodel`, `sandbox`, `sha256`, `stubs`, `sysroots`, `toml`, and `core_min` transitively) and
  `../lib/user_default.mc` (`src/user.mc:17`). **No `src/` file includes any other `lib/` file, and
  no `src/` file has a `#include <name>` of a library at all** -- the compiler declares the system
  calls it needs in its own host layer.
* **The slim flavour** ([`../reference/bundle.md`](../reference/bundle.md) § The slim flavour):
  `src/core_slim.mc` is the five parts without `<mc/core_bundle>` and `<mc/core_sandbox>`, and
  `src/main_slim.mc` the `main()` that matches. It is what `mc install`'s refusal
  (`dep_include_hint`) was written for.
* **The ten goldens** (`ls tests/golden/`): `mc2`, `mc2-opt`, and the four foreign ones each with an
  `-opt` twin. `src/mc_seed.mc` -- what the frozen seed compiles since the bootstrap decoupling --
  has relative includes only and touches no bundle.

## 1. The measurements (step 0), and what they decide

### 1.1 The blob today, with the owner's rule applied per row

678 368 B** (the blob is the names plus the streams; the index is another 3 232 B). Applying "a row
stays iff the compiler is built from it" -- which by § 0's last-but-three bullet is *the path is

### 1.2 The three binaries, measured

Measured by copying `tools/bundle.list` aside, writing the 60-row subset, running `build/bundle`, and
building with `build/mc1 --exe src/mc.mc`; then restoring both files and confirming with `cmp`:

| | binary | `__text` | `__cstring` | `__DATA,__data` | blob |
|---|---|---|---|---|---|
| `mc` today | 1 408 576 | 540 192 | 31 024 | 691 456 | 678 368 |
| `mc` with the 41 rows out (**measured, not projected**) | **1 268 276** | 540 192 | 31 024 | 566 832 | 555 053 |
| `mc-slim` (no blob at all) | 626 420 | 476 280 | 27 248 | 8 664 | 0 |

* The cut is **−140 300 B, −10.0%** of the binary and **−18.0%** of `__DATA,__data`. The blob is 98%
  of that section (678 368 of 691 456), so the section and the blob move together.
* **`__text` does not move at all.** A bundle row is data. The other 476 280 B is code, and the only
  measured lever on it is the flavour: `mc-slim`'s `__text` is 63 912 B smaller because
  `<mc/core_bundle>` and `<mc/core_sandbox>` are not in it. That is where the rest of the "enxuto"
  lives, and it belongs to whichever milestone decides whether `mc sandbox` is part of the default
  compiler (§ 13.7). M52 does not touch it.
* `mc-slim` is 44.4% of today's full binary and **49.4% of the thinned one**: after M52 the two
  flavours differ by exactly one thing, the compiler's own source, which is the honest definition
  they never quite had.

### 1.3 The four probes: does the road that is already there actually serve a library?

Run on this host with the thinned compiler of § 1.2 (`/tmp/mc-thin`), a private `HOME`, and no
network. Transcript in the commit that lands step A; the four results:

| probe | command | result |
|---|---|---|
| 1 | thinned compiler, nothing installed, `#include <sys>` | `m52probe.mc:1: unknown bundled include: sys`, exit 1 |
| 2 | unthinned `build/mc1`, same source | compiles, runs, exit 42 |
| 3 | `mc install --from-tree . --yes` into the private `HOME` | `package mc 0.0.0-dev -> …/.mc/libs/mc/v0.0.0-dev/`, exit 0, **0.28 s**, 107 files, 3 308 KiB |
| 4 | thinned compiler again, same source, **single-file CLI, no `mc.toml`, no lock** | compiles, runs, **exit 42** |

Then the road a taught compiler takes, which is the consumer's road:

| probe | command | result |
|---|---|---|
| A | thinned compiler + installed tree builds `#include <mc/host>` + `#include <mc/core>` + `#include <user_float>` | exit 0, 1 324 746 B |
| B | that compiler compiles and runs a program using `<sys>` and `<float_rt>` | prints `10.000`, exit 42 |
| C | the same taught compiler built by the **unthinned** `build/mc1` | exit 0 |
| D | the object each taught compiler writes for the same float program | **`cmp` equal** |

Probe D is the inertness proof of the whole milestone: a library's bytes are the same bytes whether
the blob or the installed tree hands them over, so nothing the compiler emits can move. Probe 4 is
the reason design (I) wins § 3: **the single-file CLI has no lock road at all**
([`../reference/packages.md`](../reference/packages.md) § 2), so step 3 is the only road that can
serve `tests/float/*.mc`, `check-float`, `check-wide` and a bare `mc prog.mc -o prog`.

### 1.4 What that decides

1. The size gain is real but modest (10%), and it is **all data**. The spec says so in its own
   headline instead of letting a reader expect a smaller compiler (§ 10.1).
2. The mechanism is not to be designed -- it is to be *reached*. The compiler-side work is a
   predicate in the generator, two more roots in one function, and one widened message (§ 2, § 4).
3. Because the spelling of every `#include <name>` is unchanged, the migration is not a source
   migration. It is a *provisioning* migration: the tree has to be somewhere. § 4 decides where.
4. The 41 rows are not 41 libraries. **17 of them, and the largest single row, are check-script
   fixtures** -- which is an argument against publishing them as packages and for keeping them files
   of the `mc` package (§ 3).

## 2. The essential set -- decision (design question 1)

**D1. A bundle row stays iff its path is under `src/`, plus exactly two named exceptions.** One
predicate, in `tools/bundle.mc`, ~8 lines:

```text
in the blob  <=>  path starts with "src/"  or  name is "prelude"  or  name is "user_default"
```

The two exceptions are not taste, they are the compiler's own `#include`s: sixteen files under `src/`
include `../lib/prelude.mc` and `src/user.mc` includes `../lib/user_default.mc` (§ 0), and inside the
blob those relative includes resolve by name to `prelude` and `user_default` (M15's last-component
fallback). Drop either and `<mc/core>` is broken and `check-standalone` fails at once. They are
"verdadeiramente dependência" in the owner's exact sense.

Three alternatives, and why not:

* **A third column in `tools/bundle.list`** (`blob` / `lib`). Honest and greppable, but the
  classification would then live in the manifest *and* `dp_mc_load` would have to stop the path at
  the second TAB (it takes the rest of the line today, `src/deps.mc:1233`). The predicate is one
  place; a column is two, plus a format change to a file an installed tree carries.
* **A second list file** (`tools/bundle.blob`). One more generated file to keep from drifting.
* **Moving `lib/prelude.mc` and `lib/user_default.mc` into `src/`**, which would remove the two
  exceptions. It would tell the truth -- they are part of the compiler's source -- and the bundled
  NAMES would not move, because the name column is independent of the path. But it churns 17
  `#include` lines for two lines of predicate, and `<prelude>` is genuinely both: the core's `while`
  and `for`, and a library every program uses. **Not done**; recorded here so the next reader does
  not rediscover it.

`tools/bundle.list` itself is **unchanged** -- all 101 rows stay, and that is load-bearing: the file
is the NAME->PATH map step 3 reads out of the installed tree (`dp_mc_load`), so a row that left the
blob must still be in the map or the library is unreachable by *either* road. The root `mc.toml`'s
105 `files` are unchanged for the same reason. **The blob shrinks; the package does not.**

## 3. Where the libraries live -- decision (design question 2)

**D2. They stay files of the `mc` package and are served by resolution step 3. M52 publishes no new
registry package.** Proven by § 1.3, at a cost of zero new resolution roads.

The alternative -- one package per library (`float`, `i128`, `f16`, `io`, `sys_linux`,
`sys_windows`, and `rt`/`http`/`sqlite` from `examples/api`), priced in
[`M47-S5.md`](M47-S5.md) § 4 as ~150 changed lines plus the moves -- is refused for M52 on three
measured grounds, not on cost:

1. **Only one bare name per package survives.** `libs_open` (`src/deps.mc:1313`) matches a lock row
   by the name's FIRST path component and then joins either the rest of the path or, for a bare
   `<geo>`, the package's `lib` entry. So a package named `float` serves `<float>` and
   `<float/machine_arm64_float.mc>` -- but **not** `<machine_arm64_float>`. Every one of the 41 names
   except at most six would have to be respelled in every consumer, including the teko compiler,
   which includes `<machine_x86_64_float>` and `<machine_arm64_float>` by their bare names today
   (§ 7). Design (I) changes no spelling at all.
2. **The single-file CLI has no lock road**, so `tests/float/*.mc`, `tests/wide/*.mc`,
   `tests/windows/07*.mc`, every `<sys>` program in `bench/`, and `mc prog.mc -o prog` itself could
   not resolve a package name without each becoming a project with an `mc.toml`. Probe 4 shows step 3
   serving exactly those.
3. **17 of the 41 rows are check fixtures** (§ 1.1). `user_syntax_demo`, `machine_probe`,
   `pass_demo`, `user_dupop` are not a standard library; they are this repository's test corpus and
   they have no consumer and no version series. A package for them would be a published artefact
   nobody installs.

What D2 gives up, and what replaces it: a project cannot pin a *newer* `float` than its compiler
ships. It can pin a newer everything -- `[deps] mc = "0.17.0"` is a legal row, `mc` is the registry's
own published package and the tree is hashed and locked like any other -- and when per-library
packages arrive (§ 9) the layering works with no change here, because step 1 precedes step 3: a
`[deps] float` pin overrides the compiler's own copy by construction.

**D3. The libraries are versioned with the compiler**, because they are files of the `mc` package and
`mc install` writes `<libs>/mc/v<mc_version()>/`. No second version series, no 1.0.0 freeze
commitment for `float`, no lockstep to maintain. This is [`M48.md`](M48.md) § 2's `mclib` rationale
with the package it already had instead of a new one -- see § 9.1 for what exactly of M48 § 2 is
superseded.

## 4. The library root, and the offline promise -- decision

**D4. `dp_mc_load` gains two more roots, tried after `<libs>`, derived from `host_self_path()`; and a
release ships the tree beside the binary.** ~15 lines in `src/deps.mc`, and it is what keeps the
property M15 earned and [`../bootstrap.md`](../bootstrap.md) asserts: untar, compile a float program,
no network.

Order, and why:

| order | root | who puts it there |
|---|---|---|
| 1 | `<libs>/mc/v<version>/` -- `--libs-dir DIR` or `$HOME/.mc/libs` | `mc install`, `mc upgrade` |
| 2 | `<dir of host_self_path()>/lib/mc/v<version>/` | the release tarball, and `make` |
| 3 | `<dir of host_self_path()>/../lib/mc/v<version>/` | a packager who puts the binary in `bin/` |

`<libs>` is first so that an explicit `mc install` still wins over the copy that shipped -- a user who
installs a newer tree gets it, which is the same precedence `--libs-dir` has over `$HOME` today.
Roots 2 and 3 are two `lex_readable` probes; root 3 exists because `/usr/local/bin/mc` has to find
`/usr/local/lib/mc/v0.16.0/`, and a packager who cannot do that will vendor the blob back in.

The tree beside a binary is a **partial** tree and that is fine by construction: `dp_mc_load` reads
`bundle.list` and `dp_mc_open` falls through on any name whose file is not readable (§ 0), so the
release stages only `bundle.list` and the `lib/` files -- about 312 KiB of source, and nothing of
`src/` (a full binary answers every `mc/*` name from its blob; a slim one needs `mc install`, exactly
as today).

**D5. `make` populates root 2 for the whole suite.** Four lines in the `Makefile` put `bundle.list`
and `lib/` under `build/lib/mc/v<version>/`, beside `build/mc1`, and **every check script then works
with no new flag, no `--libs-dir` and no dependence on `$HOME`** -- which is the CI rule
([`../reference/packages.md`](../reference/packages.md) § 2's last paragraph) satisfied by the layout
instead of by an argument. This is why `--libs-dir` is deliberately **not** added to the single-file
CLI: nothing needs it once the root is beside the binary.

**D6. The refusal is widened.** `dep_include_hint` is asked only when `bopen_fn == 0` today, so the
thinned full binary of probe 1 says `unknown bundled include: sys` and names no road. After M52 a
binary asks the hint whenever **nothing** answered, and the hint distinguishes three states:

| state | message | exit |
|---|---|---|
| no root found at all | `prog.mc:1: #include <sys>: not in this compiler and mc 0.16.0's library tree was not found: run mc install` | 1 |
| a root found, the name is not in its map | `prog.mc:1: unknown bundled include: sys` (unchanged) | 1 |
| a slim binary, no root | `prog.mc:1: #include <prelude>: not bundled in this compiler and mc 0.16.0 is not installed: run mc install` (unchanged) | 1 |

The middle row is the one that must not move: a misspelled name is still a misspelled name, and
`check-mc`/`check-surface` assert that text.

## 5. Install on demand at a build -- decision (design question 3)

The direction asks for libraries "que podem ser instaladas (caso não existam) no momento do build".
Three roads were weighed against two promises -- `mc build` never downloads
([`../reference/packages.md`](../reference/packages.md) § 9, proved by `check-pkg`'s failing `curl`)
and one source gives one answer on every machine
([`../determinism.md`](../determinism.md)).

| road | determinism | offline promise | verdict |
|---|---|---|---|
| (a) refuse, and name the command | kept | kept | **the default** (D6) |
| (b) resolve the newest implicitly and write the lock | **broken**: the answer is a function of the day the build ran | broken silently | refused |
| (c) an explicit flag that runs the sync step first | kept -- `sync` writes the lock, and the lock is what the build reads | kept: without the flag, nothing reaches the network | **D7** |

**D7. `mc build --sync` lands, and it is the only road from a build to the network.** It is
`pkg_sync(dir, yes)` followed by the build, ~20 lines in `src/driver.mc`, no new resolution
semantics, the same plan and the same `[[permission]]` consent `mc pkg sync --yes` already prints
([`../reference/packages.md`](../reference/packages.md) § 10). Without the flag `mc build` is byte
for byte the command it is today, and `check-pkg`'s `curl`-that-exits-97 keeps proving it.

(b) is refused with a number: a project whose `[deps]` names no version would resolve `float` to
whatever the index holds at that minute, so two machines and two days give two objects -- and every
gate in this repository that says "the same source twice" would be measuring the registry.

What the *common* case does after D4 is reach the network **not at all**: the tree ships beside the
binary, so `--sync` is for a project with real `[deps]` rows, which is what it was always for.

## 6. The compiler's own tests -- decision (design question 4)

**D8. `make check` runs with no network and no `$HOME`, through root 2 (D5).** No vendored `deps/`, no
local registry, no `--libs-dir` plumbing: one `Makefile` rule, and every script that reaches a
library name keeps the name it has.

What each gate needs, read from the scripts (18 of them name a library path or a bundled library
name):

| gate | what it does today | after M52 |

## 7. The consumer -- decision (design question 5)

teko reported its bundle surface on 2026-09-13, measured by grep over its own modules:

| what | includes from the bundle |
|---|---|
| the teko compiler (`teko*.tk`, `core_teko.mc`) | `<sys>`, `<mc/core_writers>`, `<mc/core_machines>`, `<mc/core_bundle>`, `<mc/core_build>`, `<machine_x86_64_float>`, `<machine_arm64_float>`, `<float>` |
| `lib/rt.tk`, `lib/time.tk` | `<name>` through `<mc/core_bundle>` only -- no `<io>`, no `<i128>` |
| `teko_std` | `<teko/lib/rt.tk>` from the registry; **zero** direct bundle |

**D9. The 0.16.0 cut needs no change in teko at all, and no deprecation window.** Every name in that
table keeps its spelling: the four `mc/*` ones stay in the blob (§ 2), and `<sys>`, `<float>`,
`<machine_arm64_float>` and `<machine_x86_64_float>` come from the library root the release ships
(§ 4). The exact `[deps]` lines teko will need are: **none.**

That is the whole value of D2 over per-library packages, and it is worth stating as the counterfactual:
under design (II) teko's compiler would need `[deps] float = "0.16.0"` plus **three respellings** --
`<float/float.mc>`, `<float/machine_arm64_float.mc>`, `<float/machine_x86_64_float.mc>` -- because only
a package's `lib` keeps a bare name (§ 3.1), and its registry `modules` array would have to carry them
ahead of `<teko/teko.tk>`.

teko's one open question -- "como um pacote de linguagem declara 'preciso do pacote float carregado
antes dos meus módulos'" -- is answered today and needs no feature: `[compiler].modules` is an ARRAY
and `drv_gen_compiler` emits one `#include` per entry **in array order** (§ 0), with a `<...>` value
passed through verbatim. So the answer is one line ahead of the language module, whether the name is
a bundled one now or a package one later:

```toml
[compiler]
modules = ["<user_float>", "<teko/teko.tk>", "<teko/user.mc>"]
```

**D12 (step D, added 2026-09-14 from the consumer's dry run against `main` 62f0cdd/21d081b).** The
table above is about a program teko's compiler compiles. What it did not cover is teko's compiler
**itself**: a `[compiler]` product is a second binary in the project's own `build/`, so roots 2 and
3 are relative to IT and the tree beside `mc` is invisible. Measured by the consumer: the product
works when `mc build` spawns it (the parent hands its root over, `deps_libs_for_child`) and fails
when run standalone -- `build/teko --entry-only ...`, its own `bootstrap.sh`, its `check-docs.sh` --
with `lib/rt.tk:40: unknown bundled include: sys`, **3 of 64 fixtures**; `--libs-dir` or a copied
tree gives 64/64 and FIXPOINT OK. Three shapes were weighed:

| shape | verdict |
|---|---|
| (a) `mc build` STAGES the tree beside the `[compiler]` product | **taken**: a taught compiler leaves `mc build` as self-sufficient as the release tarball |
| (b) bake the builder's absolute root into the binary | refused: a path in the object, against [`../determinism.md`](../determinism.md) |
| (c) `--libs-dir` on every invocation | refused: it pushes the contract onto every consumer's scripts, and breaks a user who is handed `build/teko` |

So D9 stands for the SOURCES and gains one sentence for the BINARY: the consumer's `--libs-dir`
workaround is no longer needed on any road.

**D10. No deprecation window, and no alias.** The roadmap's 1.0.0 policy (add the new, keep an alias
for one major) is about a *renamed or removed* surface. Nothing here is renamed and nothing is
removed: `#include <float>` resolves to the same bytes before and after, by a different road. A
deprecation message would fire on a spelling that is still correct. What 0.16.0 owes the reader is a
release note that says the library tree ships beside the binary and that a binary copied out of the
tarball alone loses it (§ 13.2).

## 8. Goldens, the bootstrap and the flavours -- decision (design question 6)

**D11. All ten goldens move once per step that regenerates the blob**, each only after its own

### 9.2 Per-library registry packages -- deferred, with the price and the one new fact

[`M47-S5.md`](M47-S5.md) § 4 prices the moves (`lib/float/`, `lib/i128/`, …), what breaks (the
`lib/*.mc` globs in three scripts, the paths `check-float`/`check-wide`/`check-surface` name, ~15
places in `docs/`), and answers the nesting question (`lex_root_of` keeps the LONGEST matching root,
so an inner package wins -- untested, and a nested fixture in `tests/pkg/` is the first thing that
work should add). Two things to add to that page's price:

1. **The spelling cost, measured**: 41 names, of which at most 6 could keep a bare spelling as some
   package's `lib`. The other 35 become `<pack/file.mc>` in every consumer, every test and every doc
   that names them (18 scripts, 25 `docs/` files, § 6).
2. **The single-file road**: a package name is unreachable without a project (§ 3.2), so the move
   turns `tests/float/*.mc`, `tests/wide/*.mc` and the `<sys>` programs of `bench/` into projects, or
   requires a new resolution road for them.

When it happens, the shape is one package per directory under `lib/<name>/`, `[package] name/lib/
files/mc/licence`, `[[permission]]` empty (a library asks for nothing -- it runs inside the caller's
program, which is what `packages.md` § 3 already says of a library's permissions), versions starting
at the compiler's own minor, and **the names registered by the owner first**: `float`, `io`, `sys`,
`i128`, `f16`, `prelude` are not in `dep_reserved`'s set (§ 0) and any account can take them today.
That is a registry action, not a compiler one, and it is the one item of § 9.2 worth doing **before**
0.16.0 ships (§ 13.4).

### 9.3 M51's `<http>`

**D13. M51 ships `http` as a registry package, never as a bundle row.** The direction's first clause
-- "M51 não violaria se fosse lib, não bundle" -- is settled by § 2's predicate: `lib/http.mc` would
have a `lib/` path and would therefore not be in the blob, so the question is only whether it is a
file of the `mc` package or a package of its own. It is a package of its own, because HTTP is not a
dependency of the compiler and its release cadence is not the compiler's -- which is the owner's rule
applied to the one library that has a consumer outside this repository. M51 is therefore the **first**
package of § 9.2, and it inherits § 9.2's two costs: `bench/http/`'s single-file programs
(`forkka.mc` 53 lines, `fork1.mc` 50, `httpmin.mc` 124) become a project with an `mc.toml`, and the
name `http` wants registering before the first tag. `examples/api/lib/http.mc` (253 lines) and
`rt.mc` (253) are where the shape comes from; `bench/http/mc/forkka.mc` is the shape M51 packages.

## 13. Risks

1. **The consumer.** Measured at zero include rewrites (§ 7) and zero `[deps]` lines. The residual is
   provisioning: if teko's CI copies the `mc` binary out of a tarball and discards the rest, `<float>`
   stops resolving. Named in the release note, and `check-libroot` is the gate that keeps the three
   roots working.
2. **"The binary alone is the toolchain" is weakened for library names.** This is real and it is the
   price of the direction: before M52 a copied binary compiled a float program; after it, the binary
   plus the `lib/` directory beside it does. `docs/bootstrap.md`'s claim must be rewritten to say
   *the compiler's own source* is inside the binary -- which is still the strong claim, and the one
   `check-standalone` proves. A user who wants the old behaviour has `mc install` and a project has
   `[deps] mc`.
3. **The library root is unverified.** Step 3 hashes nothing (§ 0), so a tampered `lib/` beside the
   binary is compiled without complaint, where the blob was inside a signed executable. Exactly as
   true of `mc-slim` today, which shipped. The answer for a consumer who needs verification is the
   lock road -- `[deps]` + `mc.lock`, hashed per file -- and a hash check on root 2/3 is priced as a
   follow-up (a `v<ver>.toml` cache manifest already exists for `mc install`'s road; the beside-the-
   binary road would need one written at release time).
4. **Name squatting.** `float`, `io`, `sys`, `i128`, `f16`, `prelude`, `http` are not reserved
   (`dep_reserved`, § 0) and § 9.2/§ 9.3 will want them. Registering them before 0.16.0 is a registry
   action with no compiler cost, and it is the cheapest item on this page.
5. **Registry availability at build time** is a risk only for `mc install` on a slim binary and for
   D7's `--sync`. `mc build` without the flag still never calls out (§ 5), so a registry outage
   cannot stop a build of a locked or vendored project.
6. **CI minutes for per-package repositories** -- deferred with § 9.2. One `publish-to-registry` job
   per package is the shape; M48 § 2.2's road-A table is the price.
7. **The other 476 KB is code, and this milestone does not reach it.** § 1.2 measures where it is
   (`__text` 540 192, of which 63 912 is `<mc/core_bundle>` + `<mc/core_sandbox>`). If the owner
   wants the binary leaner than 1.27 MB the lever is the flavour, not the blob, and the question is
   whether `mc sandbox` belongs in the default compiler -- M43's call, not M52's.
8. **Two golden rewrites in one milestone** (D11) read like a mistake in a log. Recorded in the
   step table and in `CLAUDE.md` § State.
9. **A future `src/` file that should NOT be in the blob**, or a `lib/` file that should be, would
   make § 2's path rule wrong. The escape is the third column § 2 priced and refused; it is 10 lines
   whenever the first counter-example arrives.
10. **`check-docs` fences.** Six `docs/` pages have ```mc fences that include a library name; if the
    root is not visible to the script, the gate fails loudly rather than silently, which is the
    behaviour wanted.

## Implementation notes -- step A

Written after the fact, against the tree that landed. The design above is unchanged; what follows
is what the code and the gates actually do, and the four places the text and the tree had to be
reconciled.

1. **The three roots are one function**, `dp_mc_root()` in `src/deps.mc`, and `dp_mc_load` calls
   it where it used to build `<libs>`'s path inline. A root is recognised by its `bundle.list` and
   by nothing else: the first root that HAS that file is the only one read, so a `<libs>` tree
   that exists but is empty does not silently fall through to the one beside the binary and hand a
   reader a library he did not install. Roots 2 and 3 come from `path_join(host_self_path(), ...)`
   -- `path_join` cuts its base at the last slash, which is exactly "the directory of this file",
   and normalises the `..` of root 3 lexically.

2. **A self path with no slash in it is refused.** `host_self_path()` is `_NSGetExecutablePath` /
   `readlink /proc/self/exe` / `GetModuleFileNameA` and all three normally answer a path with a
   directory in it, but `path_join` with a base that has none answers a RELATIVE path, which would
   make the root a function of the working directory. Four lines say no instead
   (`docs/determinism.md`: one source, one answer, wherever `mc` was run from).

   `lex_readable`, and it is compiled after `src/lex.mc` in every assembly that contains it

   added to the hook.

4. **`scripts/libroot.sh` is the one definition of the tree** and both the `Makefile` and
   `scripts/release-assets.sh` call it. Writing the copy twice was the alternative and it is the

## Implementation notes -- step C

Written after the fact. The flag is the design's; what follows is the one place the design did not
look, the one number `pkg_sync` could not answer on its own, and what the gates measure.

1. **The driver may not NAME `pkg_sync`.** `src/driver.mc` is `<mc/core_build>` and `src/pkg.mc` is
   `<mc/core_pkg>`, and `check-parts` § 1b requires each part to compile on `<mc/core_min>` alone --
   so a direct call would have made the driver drag the fetcher, the registry and the lock writer
   into every compiler that has `mc build`, which is exactly the split `docs/reference/packages.md`
   § 9 rests on ("a compiler assembled without `<mc/core_pkg>` cannot download even in principle").
   The sync step therefore arrives as a **pointer**, `drv_set_sync(&pkg_sync_for_build)` from
   `mc_pkg_init()` -- the shape `lex_set_bundle` and `lex_set_libs` already have. It is a field of
   the driver's own record (`DRV_SYNCFN`), not a global, so the globals row did not move.
   Measured: `--dump-syms` of a compiler assembled from `<mc/core_min>` + `<mc/core_machines>` +
   `<mc/core_writers>` + `<mc/core_build>` has `_drv_build` and no `_pkg_sync`, and
   `mc build DIR --sync` on it is `mc: --sync needs the package half of this compiler: mc pkg is
   not in it`, exit 1 (`scripts/check-parts.sh` § 4c).

2. **`pkg_sync` returns 0 for two different outcomes, and a build has to tell them apart.** For
   `mc pkg sync` "the lock is written" and "I printed a plan and did not run it" are the same
   answer -- it said what it would do -- and both are exit 0. For a build they are not: in the
   second case the lock was not rewritten, so the build would either read a stale one or refuse.
   The wrapper `pkg_sync_for_build(dir, cfg, yes)` is what adds that one bit, and it adds nothing
   else: `pkg_open_config` + `pk_set_yes` + **the same `pkg_sync`**, then
   `if (!pk_yes() && (pk_nplan() > 0 || pkg_perm_ask())) return -1;`. `-1` is "stop, exit 0": the
   plan is on the screen and nothing else happened. The permission half is not decoration -- a
   build that walked past an unaccepted `[[permission]]` set would be a second road around the
   consent `mc pkg sync` asks for.

3. **The flag is not forwarded to the `--entry-only` child, and that is by construction rather
   than by a line.** `drv_teach` writes the child's argv name by name (`build`, the directory,
   `--config`, the config, `--entry-only`, then `--libs-dir`/`--opt=`/`--limits` when they apply),
   so a flag it does not mention cannot travel. The gate measures the consequence instead of the
   code: `tests/pkg/sync/teach.toml` is the same project with a `[compiler]` section, and
   `mc build --sync --yes` on it prints **one `lock` line and two `fetch` rows**, not two and four.
   A second sync in the child would have rewritten the lock a second time and said so.

4. **`mc build` has no `--registry`, and does not get one.** The registry is `[registry].url` or
   the default. A build whose answer depended on a registry named in the shell line would be a
   build two people cannot reproduce from the same checkout, which is the same argument § 5 used
   to refuse implicit resolution. `scripts/check-pkg.sh` § 38 names its fixture registry by
   `sed`-ing a `[registry]` table into a copy of the project's config, which is what a private tap
   looks like in real life.

5. **The `run:` line did not change**, against the step table's "the `run:` line it makes
   unnecessary" read as a licence to rewrite it. `mc: mc.lock is stale` and `mc: <pack> <ver> is
   not fetched` still say `run: mc pkg sync --yes`, for two reasons: the refusal is raised by
   `src/deps.mc`, which is `<mc/core_build>` and has no business naming a flag that needs the other
   part; and the advice is right on every road -- `mc pkg sync --yes` works whether or not the
   reader is inside a `mc build`. What `--sync` makes unnecessary is the second COMMAND, not the
   sentence. `check-mc` and `check-pkg` assert that text and neither moved.

6. **`--yes` on its own is refused**, not ignored (`mc: --yes applies to --sync: mc build downloads
   nothing without it`) -- the post-M42 rule for a flag read by nobody. Both flags live in ONE
   record field, `DRV_SYNC` (0, 1, 2), so `drv_run` needed no new parameter and its three callers
   (`drv_build`, `drv_limits`, `sysroot_cmd`) were not touched; `mc limits` and `mc sysroot stub`
   parse no `--sync` and read 0.

7. **A part-less compiler still ADVERTISES the flag.** The usage line is
   `subcommand("build", ...)`'s, registered by `<mc/core_build>`: a subcommand disappears with its
   part (M43 § 4b, `mc sandbox`), a flag inside one cannot. The refusal is what tells the truth, and
   it names the missing half. Re-registering `build` from `mc_pkg_init()` with a longer usage string
   was the alternative and it puts the same text in two files -- the one drift nobody would notice.

8. **A no-op sync stays a sync.** `mc build --sync` on a project with no `[deps]` and no `[tools]`
   is `sync: no dependencies`, an empty `mc.lock`, and the build: that is what `pkg_sync` does
   there, and making the build skip the step would have been a second behaviour to remember.

9. **Cost: 79 added lines in `src/`, 30 of them neither comment nor blank** (`src/driver.mc` +48/-1,
   `src/pkg.mc` +25, `src/core_pkg.mc` +5, `src/core_build.mc` +1/-1), against the step table's
   ~20. Zero new globals: `mc limits src/mc.mc` reports the same `globals` row before and after.
   Nothing the compiler emits moved -- `scripts/check-inert.sh` against the fork point is 33
   objects identical on the plain road and 33 with `--opt=1`, plus the five taught examples.

   consumer's own message, `unknown bundled include: sys`, is the third: a product that has
   `<mc/core_build>` and therefore a resolution road, with no tree at the end of it.

2. **`make check-lang` passes today for a different reason than adjacency, and that was
   checked rather than assumed.** `examples/lang/build/mc-lang` is nowhere near the repository's
   `build/lib/`; what saves it is that `grep '#include <' examples/lang/*.lx lib/*.lx *.mc` finds
   **no library name at all** -- the only bundled include in the directory is `<mc/core>` in a
   comment. It never asks step 3 a question.

3. **The staging is `drv_stage_libroot(drv_path(cbin))` in `drv_teach`, one call for both roads**
   (the `--compiler-only` half returns after it). The source is the root the RUNNING `mc` resolved
   for itself, read off the map `dp_mc_load` already parses and caches -- `src/deps.mc` is
   included before `src/driver.mc` in `<mc/core_build>`, so the driver calls `dp_mc_load()` and
   `dp_state()` and reads `DP_MCDIR`/`DP_MCN`/`DP_MCPATH` through that file's own `#define`s.
   The alternative, `bundle_read` of each `lib/` row, is **not open to the driver**: it is the
   same part split step C's note 1 records -- `src/driver.mc` is `<mc/core_build>` and
   `bundle_read` is `<mc/core_bundle>`, so it would need a fourth function pointer. And after
   step B it would answer almost nothing: the blob keeps `src/*` plus `prelude` and
   `user_default`, so a binary with no root has no library to stage.

3b. **The whole thing is ONE function, and the frozen seed is the reason.** The first draft was
   five -- three readers in `src/deps.mc` and a `drv_stage_file` helper -- and it turned
   `make check` red in a place nothing else in this branch touches: `scripts/check-asm.sh`
   compiles `lib/mc_i128.mc` and `lib/mc_u128.mc` with `build/mc0`, and those are
   `#include "../src/core.mc"` plus a module, i.e. the whole compiler in one translation unit.
   `mc limits` puts them at **2044 of the seed's `MAXFUNCS` 2048** on `main`; five more is 2049
   and `build/mc0` answers `mc: too many functions`, exit 1, `176/178 files identical`.
   `stage0/` is frozen, so the budget is what had to give: one function is **2045, three of
   headroom**. Worth recording for whoever writes the next `src/` milestone -- that ceiling, and
   not `check-limits`' own rows (which measure `src/mc_seed.mc`), is the tight one.

4. **The rule is `scripts/libroot.sh`'s, restated in one loop**: `bundle.list` plus
   every row whose path is not under `src/`, and only the files that are there. Writing a
   different rule in the compiler than the one the release tarball is laid with is step A note
   4's drift with the two sides swapped. Measured: **44 files**, the same count and the same
   bytes `sh scripts/libroot.sh` writes.

5. **Idempotence is a byte compare, not a timestamp.** The loop reads the destination and does
   not write when the lengths and the bytes match, so a second `mc build`
   rewrites nothing -- proved with a marker file and `find -newer`: **0 of 44**. A timestamp
   comparison would have been wrong on a checkout, where every source is newer than every
   artefact.

6. **`deps_libs_for_child` is kept**, and the reason is worth a line: with the staging in place
   the spawned child would find its own root 2 anyway, but the parent's `--libs-dir` still
   *wins* (root 1 beats root 2, D4) and it is what makes the child's resolution order identical
   to the parent's on the road where the two could differ -- a `<libs>` the parent read and the
   child's freshly staged copy are the same bytes, but only one of them is what the parent
   actually compiled against. It is also why the staging changes no artefact: on the `mc build`
   road the staged tree is never read.

7. **The gate is `scripts/check-libroot.sh` case (g)**, which is where the other roots are
   proved. Its fixture is the consumer's shape reduced to what a gate can run in seconds:
   `core = "<mc/core_min>"` and a module that is `examples/avr/mc-avr.mc` minus the AVR --
   `<mc/core_machines>`, `<mc/core_writers>`, `<mc/core_build>`, a `main()` and an empty
   `user_init()`. **No `<mc/core_bundle>`**, so the product has no blob and a successful
   `#include <sys>` is road 3 through the staged tree and nothing else. Three assertions: the
   tree is there (44 files), the product run standalone compiles and RUNS the program (exit 42)
   with an empty `$HOME` and no `--libs-dir`, and a second build rewrites 0 files.
   `<mc/core_build>` is in that list for a measured reason: without it `mc_build_init()` never
   runs, `lex_set_libs` is never called, and the product has no road 3 to reach a tree with --
   the first draft of the fixture left it out and answered `unknown bundled include: sys` with
   the tree sitting beside it.
