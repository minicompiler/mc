# Spec M53 -- the surface freeze, the deprecation policy and the release canary: the road from 0.16.0 to RC 0.17.0 and to 1.0.0

Written against `minicompiler/mc` `main` at `5dd6c90` (newest tag `v0.16.0`), read-only session
except for the extractions of § 1, 2026-09-14. [`../plan.md`](../plan.md)'s row is written from this
spec and not the other way round.

The owner's direction, verbatim:

> Congelar a superfície — RC 0.17.0 — crítico. Política de deprecação (hooks.md § Stability): de
> 1.0.0 sem rename seco — adiciona novo + alias por um major, remoção = MAJOR. Formatos,
> mc.toml/mc.lock, nomes `<mc/*>` e a versão congelados = semver de verdade.

> Melhorias + canário — antes de cortar: a release do mc dispara o CI da teko antes de publicar
> (bloqueante no 1.0.0). Sem credencial — a teko puxa a release pública do mc.

> A 1.0.0 sai quando a lista de lacunas da teko chega a zero — ela auto-hospeda nas 5 pernas e
> publica a teko_std sem pedir gancho novo ao mc.

The one-paragraph version. The measurements move this milestone twice. First, **the inventory
already exists and nobody reads it as one**: `scripts/check-docs.sh` extracts the whole public
surface from `src/` on every `make check` -- 206 symbols, 50 CLI flags, 35 TOML keys, 10 directives
-- and then throws it away after asking "is each one documented?". Asking the second question, "was
each one here last time?", costs one recorded file and one comparison. Second, **the extraction has
a hole and the hole is exactly where a freeze would hurt most**: `val_reg`, `dst_reg` and `dst_done`
are the three names [`../reference/machine.md`](../reference/machine.md) § 3 publishes as *the only
three names of a machine's internals that are frozen* (contract version 3, M24 D2), and they match
none of the 17 prefixes and none of the 5 exact names the extraction knows -- **0 of 206**. A gate
built on today's regex would have frozen 206 names and left the three that were already promised
unprotected. So M53 is not a policy document with a script attached: it is one shared extractor
(`scripts/surface-extract.sh`, the single definition both gates read), one recorded golden
(`tests/golden/surface.txt`, **420 lines** across seven kinds), one gate (`check-freeze`), the
policy text `hooks.md` has never had, and a `promote` job that turns every release into a GitHub
pre-release until a public verdict file teko writes says it built. **`src/` is untouched, `stage0/`
is untouched, and not one golden moves** -- which is what makes a freeze milestone safe to land
between a minor and an RC.

| `flag` | `str_eq`/`opt_val` literals in `src/*.mc`, plus `-o` (`:112`) | **50** |
| `toml` | `toml_*("literal")` + the two walked prefixes (`:130`, `:132`) | **35** |
| `dir` | `dir_index()` in `src/lex.mc` (`:149`) | **10** |

The symbol families, largest first: `gen_` 46, `p_` 25, `host_` 20, `backend_` 17, `sec_` 15,
`type_` 12, `syntax_` 12, `sym_` 11, `machine_` 9, `walk_` 7, `intrinsic_` 6, `decl_` 6, `on_` 4,

### 1.2 What the extraction does NOT see -- four holes, measured

**a. Three names that were already promised.** `docs/reference/machine.md` § 3 ("The allocator
functions a task handler may call", and version 3's changelog entry) publishes `val_reg(d, scratch)`,
`dst_reg(d)` and `dst_done(d, reg)` as *the only three names of a machine's internals that are*
frozen. `docs/reference/hooks.md:546` repeats it. All three are defined in `src/machine_arm64.mc`
(`:161`, `:181`, `:186`), are read by `lib/machine_arm64_float.mc`, `lib/machine_x86_64_float.mc`,
`lib/i128.mc`, `examples/avx/avx.mc` and `examples/kernel/machine_riscv64.mc` -- and match **none**
of the 17 prefixes and none of the 5 exact names. `grep -cx val_reg` against the extracted list:
**0**. This is the found defect, and by the owner's rule it is fixed, not voted: step A adds three
exact names and the inventory becomes **209**. `check-docs` stays green without a doc edit, because
all three are already written as calls in the reference (`machine.md:215`, `:762`, `:763`).

**b. The lock and index row keys are invisible.** `mc.lock`'s `[[package]]` rows and the registry
index's `[[versions]]` rows are read with `toml_get(tm_cat(key, "version"))` -- a computed path, not
a literal -- so `check-docs.sh:130`'s regex cannot see one. Extracted separately from
`tm_cat(key, "...")` in `src/pkg.mc`, `src/tool.mc` and `src/deps.mc`: **14 keys** -- `bin deps kind
lib licence name path permissions sha256 strip tools url version yanked`. These are a FORMAT written
by one version and read by another and by the registry; the direction names `mc.lock` explicitly.
They become the seventh kind.

**c. 448 globals, of which a handful are genuinely read from outside `src/`.** The naive
word-boundary grep over `lib/`, `examples/`, `tools/` and `site/gen/` gives 30 candidates, most of
them false positives (`cp`, `pe`, `heap`, `nodes`, `locals`, `sections`, `symbols` are ordinary local
names in unrelated files). The ones verified by reading the hit: `a64_out`
(`lib/machine_arm64_float.mc:503`), `x86_shadow`/`x86_nargreg`/`x86_argreg`
(`lib/machine_x86_64_float.mc:283-311`, `lib/i128.mc`), `x86_tmp` (`examples/avx/avx.mc`),
`walk_fn_ret` (`lib/i128.mc:627`), `nnodes`/`nodes` (`lib/pass_demo.mc:5-17`), `ty_i32`
(`examples/avr/mc-avr.mc:70`), `bundle_blob` (`tools/bundle.mc`). Roughly **ten of 448**. § 3
decides.

**d. Diagnostic text.** `docs/reference/diagnostics.md` documents **373** rows across 15 sections.
The number a gate actually asserts, counted over `scripts/*.sh`: **19** distinct `mc: …` literals,
of which `check-surface.sh`'s 18 `err_case` calls are most. So 95% of the messages are documented and
protected by nothing. § 3 decides.

### 1.3 What the release pipeline does with a candidate today

Measured by reading, not by cutting a tag: `autotag.yml` and `tag.yml` both refuse a `-` suffix, so
the only way to a pre-release version string is a hand-pushed tag, *"deliberately outside the
automation"* ([`../ci.md`](../ci.md) § Versioning). `release.yml` handles such a tag correctly
(`:649`). And a pre-release version would then be **skipped by the compiler's own resolver**:
`pkg_newest`/`pkg_pick` take a `pre` flag that is 0 for `mc pkg add NAME` and for a plain
`mc update` (`CLAUDE.md` § State, the 0.15.1 entry: *"a candidate is never chosen for you"*), and
`mc upgrade` resolves through the same row. So a `1.0.0-rc.1` is a version **nobody would install**,
which is the opposite of what a release candidate is for.

### 1.4 What that decides

1. The inventory is not new work: it is the four pipelines that already run, plus three exact names
   and one more grep. **One extractor, read by both gates** -- otherwise § 11.3's drift risk is real
   and the two regexes part company on the first edit.
2. The freeze has to cover names the extraction cannot see today (1.2a, 1.2b), and must **not** try
   to cover 448 globals or 373 message texts (1.2c, 1.2d) -- see § 3 for the arguments, which are
   different in each case.
3. "RC" cannot be a version suffix (1.3). It is a state of the repository between two ordinary tags,
   and the *candidate* semantics live in the GitHub release's pre-release flag, where the canary can
   act on them. § 7.
4. The canary needs nothing built for it on the mc side that does not exist: a pre-release flag
   (`:649`), a post-publish job with no secret (`:685`), and a public URL to read.

## 2. What "the surface" is -- decision (design question 1)

**Seven kinds, each with a single source of truth in the tree, none written by hand.**

| kind | is | source of truth | today |
|---|---|---|---|
| `sym` | a function a module outside `src/` may call | `src/*.mc`, `surface-extract.sh`'s prefix + exact-name list | **209** |
| `flag` | a command-line option `mc` accepts | the `str_eq`/`opt_val` literals in `src/*.mc`, plus `-o` | **50** |
| `toml` | a key `mc.toml` may carry | the `toml_*("literal")` calls and the two walked prefixes | **35** |
| `dir` | a `#directive` | `dir_index()` in `src/lex.mc` | **10** |
| `bundle` | a name `#include <…>` resolves | column 1 of `tools/bundle.list` | **101** |
| `lock` | a key of an `mc.lock` or index row | the `tm_cat(key, "…")` literals in `src/pkg.mc`, `src/tool.mc`, `src/deps.mc` | **14** |
| `machine` | the machine task contract's version | the `Contract version N` line of `docs/reference/machine.md` | **1** |

**420 lines.** Notes on the three that are not simply "what `check-docs` already extracts":

* **`bundle` covers the `<mc/*>` names AND the parts, in one kind.** A part is named exactly the way
  a library is -- `[compiler].core = "<mc/core_min>"` is the string teko writes, and it is
  `tools/bundle.list` column 1. Giving parts a kind of their own would be a second spelling for one
  string. 57 of the 101 are `mc/…`; M52 moved 41 of the 101 out of the blob and into
  `lib/mc/v<ver>/` **without changing a single name**, which is the proof that the name and not the
  road is the surface.
* **`lock` is a format, and the direction names formats.** Its 14 keys are what one version writes
  and another reads, and what the registry's validator reads too. A key silently dropped from the
  writer is a lock an older `mc` cannot use; a key dropped from the reader is a lock a newer `mc`
  ignores. Both are the gate's business.
* **`machine` is one line, not 37.** The contract already versions itself with an append-only rule
  and a written changelog (§ 0). Listing 37 `MTASK_*` names would duplicate `machine.md` badly -- the
  contract's promise is about *order and signatures*, which a name list cannot express. One line,
  `machine<TAB>5`, and the rule is: **the number may only go up, and only in a commit that adds a
  version paragraph to `machine.md`.** A DOWN move or a silent change fails `check-freeze`.

`mc.toml` and the registry index row are covered by `toml` and `lock` between them. `mc --version`'s
output shape is covered by `flag` (`--version`) plus § 5's behaviour clause.

## 3. What is deliberately NOT the surface -- decision

Three exclusions, each with its own argument. This section exists because a freeze that says "and
everything else too" is a freeze nobody can land.

**a. File-level globals in `src/` are NOT API.** 448 of them (§ 0), and freezing the set would make
every internal of the compiler permanent: M48 C0's diet -- twelve `src/driver.mc` globals folded into
one arena record so that `check-limits` stayed under the frozen seed's `MAXGLOBALS` -- would have
been a MAJOR, and the seed's `globals` row is the tightest in `check-limits` precisely because that
kind of work has to stay possible. The rule instead, and it is already what `machine.md` § 3
practises: **a module reads a compiler internal through a function, and the function is frozen.**
`val_reg`/`dst_reg`/`dst_done` are the three the contract publishes by name; `walk_ret_type()` and
`x86_argreg_at(slot)` are the shape for the rest. A consumer that needs a global asks for an
accessor, the accessor lands as an additive MINOR, and it is in the inventory from that day.

Two things keep this honest without a new gate. First, **the in-repo consumers are the gate**: nine
modules under `lib/` and `examples/` read the globals of § 1.2c, and `check-float`, `check-wide`,
`check-surface`, `check-kernel`, `check-avr` and `check-inert` are red the moment one is renamed --
`a64_out` cannot be renamed quietly today. Second, the policy carries one operational sentence for
the out-of-tree consumer: **a rename or removal of a `src/` global goes in the release note**, which
is what the memory rule (teko, 0.15.12) actually asked for and costs nothing to obey.

**b. Diagnostic TEXT is not API; the exit code and the stream are.** 373 documented messages, 19
asserted by a gate (§ 1.2d). Freezing 373 English sentences would make every improvement to a
message a MAJOR, and messages are the part of a compiler that most deserves improving. What a
program may rely on is what a program can act on: **the exit code and whether the text went to
stderr**. Both are already documented per family in `diagnostics.md` § The four shapes and § 11's
exit-code-2 section. The 19 that a gate asserts are protected by that gate -- changing one turns
`make check` red, which is exactly the "you will notice" a freeze needs -- so no new mechanism is
bought for them. The policy says: **a message's wording is a PATCH; its exit code is a MAJOR.**

**c. The `-opt` road, the goldens and the object bytes are not the surface either.** They are the
*determinism* promise ([`../determinism.md`](../determinism.md)), they already have ten gates, and
they move by design whenever the compiler improves. A freeze on emitted bytes would forbid the
optimizer. Named here only because "freeze the formats" could be misread to include them: an object
file's LAYOUT is frozen by its own standard (Mach-O, ELF, COFF) and by `check-obj` against the
frozen seed; its CONTENT is not.

## 4. The mechanism -- decision (design question 2)

### 4.1 One extractor

`scripts/surface-extract.sh` prints the inventory to stdout, `kind<TAB>name`, bytewise-sorted
(`LC_ALL=C sort`). It is the ONLY definition of any of the seven lists. `scripts/check-docs.sh` is
rewritten to call it (`surface-extract.sh sym`, `… flag`, `… toml`, `… dir`) instead of carrying
four `grep -hoE` pipelines of its own -- it loses about 20 lines and its behaviour, its four `ok
coverage:` lines and its counts are unchanged except that `sym` goes 206 -> 209. That is the whole
answer to § 11.3: two regexes that must agree are a bug waiting; one regex cannot disagree with
itself.

### 4.2 The recorded file

`tests/golden/surface.txt` -- under `tests/golden/` and not `docs/reference/` because it is a
*recorded artefact compared on every run and rewritten only on purpose*, which is that directory's
whole meaning, and because a reader looking for the surface should be sent to
`docs/reference/hooks.md`, not to a 420-line list. Format:

```
# mc public surface -- recorded by scripts/check-freeze.sh --record.
# One line per entry: <kind> <TAB> <name> [<TAB> deprecated <version> -> <replacement>]
# See docs/reference/hooks.md § 8 (Stability) before editing this file by hand. Do not.
bundle	float
bundle	mc/core_min
...
dir	define
flag	--exe
lock	permissions
machine	5
sym	val_reg
toml	project.opt
```

Sorted by kind then name, bytewise, so a diff is readable and a merge conflict is local.
`tests/golden/README.md` gains a paragraph.

### 4.3 The gate

`scripts/check-freeze.sh` (`make check-freeze`, inside `make check`). It re-extracts and compares:

| what it sees | verdict | what it prints |
|---|---|---|
| identical | **ok** | `ok freeze: 420 entries (209 sym, 50 flag, 35 toml, 10 dir, 101 bundle, 14 lock, 1 machine)` |
| an entry gone, not marked `deprecated` | **FAIL** | the kind and name of each, then `a removal is a MAJOR (docs/reference/hooks.md § 8). Deprecate it first, or re-record deliberately with scripts/check-freeze.sh --record.` |
| an entry gone, marked `deprecated` | **FAIL until re-recorded** | the same, minus the first sentence: the removal is legal, the file must be updated in this commit |
| an entry added | **FAIL until re-recorded** | `new: sym foo -- additive, a MINOR. Re-record: scripts/check-freeze.sh --record` |
| `machine` moved down, or changed with no new version paragraph in `machine.md` | **FAIL** | `the machine contract's version went 5 -> 4` / `… -> 6 with no "Version 5 → 6" paragraph in docs/reference/machine.md` |

**Re-recording is a flag, `--record`, not the goldens' delete-and-rerun.** The hash goldens are
rewritten by deleting the file because nobody reads their content; this file's content is the review
artefact -- the diff *is* the API change -- so the command that writes it should be nameable in a
commit message and the file should never be re-created from nothing by accident.

**Every change to the surface therefore costs one extra committed line in the same pull request**,
which is the point: an addition is cheap and visible, a removal is impossible unless deliberate.

### 4.4 What the gate does not do

It does not know what version it is (§ 0: the tree says `0.0.0-dev` and a gate asserts it), so it
cannot check that a deprecation has aged one major. That check is the `release:major` label on the
pull request, which is a human decision `autotag.yml` already reads
([`../ci.md`](../ci.md) § 2). The gate's job is narrower and complete: **a removal cannot happen by
accident, and cannot happen at all without a diff a reviewer reads.**

## 5. The policy -- decision (design question 3)

New section `docs/reference/hooks.md` § 8, *Stability*, ~90 lines. One-line pointers to it from
`cli.md`, `toml.md`, `directives.md`, `packages.md`, `bundle.md` and `machine.md`, and a row in
`docs/ci.md` § Versioning's label table.

### 5.1 The rules

| change | bump | example |
|---|---|---|
| a message's wording; a fix with no inventory line moved | **PATCH** | 0.15.37's registry-index fix |
| a new entry of any kind; a new `MTASK_*` slot under the null-slot rule; a new accessor for a global | **MINOR** | M49's six slots, version 4 → 5 |
| an entry REMOVED; a signature changed; an exit code changed; behaviour a conforming module can observe changed; a machine-contract change that is not append-only | **MAJOR** | none yet |

*Conforming* carries weight: a module that reads a `src/` global, asserts a message's wording, or
depends on an emitted byte is not conforming, and § 3 says so in the same page.

### 5.2 The deprecation lane

From 1.0.0 there is **no dry rename**. To replace `old` with `new`:

1. Add `new`. It is a MINOR and it appears in the inventory.
2. Keep `old` as an alias -- for a symbol, a one-line wrapper that calls `new`; for a flag, a TOML
   key, a directive or a bundle name, the existing parse site accepting both.
3. Mark the old entry in `tests/golden/surface.txt`:
   `sym<TAB>old_name<TAB>deprecated 1.1.0 -> new_name`. **The version is written by a human**, because
   the tree cannot know its own (§ 0); the reviewer checks it against the tag the pull request will
   cut.
4. Remove `old` no earlier than the next MAJOR, in a pull request labelled `release:major`.

One major of overlap, exactly as the direction says. The deprecation marker is the only expressible
removal, and § 4.3 is what makes that true mechanically.

### 5.3 The note, specified and priced, NOT built

A deprecated name should say so. Decided:

* **Where a name is parsed from text** -- a CLI flag, a TOML key, a `#directive`, a bundle name --
  the compiler prints **once**, to stderr:
  `mc: --old-flag is deprecated since 1.1.0, use --new-flag`. Four sites
  (`src/cli.mc`'s option loop, `toml_get`'s callers via one helper, `do_directive`,
  `lex_include_name`), one shared `dep_note(kind, old, since, new)` with a seen-bit per entry so a
  build says it at most once per name. **~25 lines of `src/`, and 0 globals** (the table is a field
  of an existing record).
* **For a symbol, the compiler says nothing.** There is no parse site: a symbol name is resolved by
  the linker, and a wrapper that printed would put a message on the stderr of every *taught
  compiler* that still calls it -- and a taught compiler's stderr is its own product, not mc's. The
  deprecation for a symbol lives in the inventory, in `hooks.md` and in the release note.

**M53 ships no deprecation, so it ships no note**: the 25 lines land with the first one, and this
section is what that pull request implements. Writing them now would be 25 lines of `src/` that no
test can exercise, which is 25 lines that rot.

### 5.4 What 0.x may still do, and when the promise starts

| period | what the gate does | what a removal costs |
|---|---|---|
| **0.16.x** (today) | `check-freeze` does not exist | nothing -- 0.x semver lets a minor break |

## 6. The canary -- decision (design question 4)

**Constraint, from the direction: no credential.** mc cannot dispatch a workflow in teko's
repository (that needs a PAT) and teko cannot receive mc's `release` webhook (a foreign repository
does not get one). Both halves are therefore **pull**, and the only thing that crosses the boundary
is a public URL each side can read anonymously.

### 6.1 The protocol

```
  mc: publish ──► GitHub Release created as a PRE-RELEASE, all assets attached
                          │
  teko: schedule (15 min) │ GET /repos/minicompiler/mc/releases   (public, no token)
                          ▼
                  newer pre-release than its pin? → run the whole recipe against the tarball
                          │
                          ▼  writes with its OWN GITHUB_TOKEN, to its own repo
        raw.githubusercontent.com/teko-org/teko-lang/canary/<version>.json
                          │
  mc: promote ◄───────────┘ polls that URL every 60 s, up to 90 minutes
        ok   → gh release edit "$TAG" --prerelease=false
        fail → job RED, the release stays a pre-release, nothing is unmade
        timeout → advisory before 1.0.0, RED at 1.0.0
                          │
                          ▼
  mc: publish-to-registry  needs: promote   (a pre-release must not become the newest row)
```

### 6.2 The five decisions inside it

1. **Every release is born a pre-release while the canary is armed.** `release.yml`'s `publish` job
   passes `--prerelease` whenever `vars.MC_CANARY == 'true'`, not only for a `-`-suffixed version
   (`:649`'s `case` stays, OR'd with the variable). The assets, the checksums and the body are
   identical; the flag is the only difference, and it is the one thing GitHub lets a later job flip.
2. **The verdict is a file at the ROOT of a branch named `canary`** in teko's repository,
   `<version>.json` — *not* `canary/<version>.json`, which would put a second `canary` in the path,
   since the branch already occupies the ref position. Read at
   `https://raw.githubusercontent.com/<owner>/<repo>/canary/<version>.json`, which for the consumer
   registered on 2026-09-14 is `teko-org/teko-lang`:
   `{"version":"0.17.0","status":"ok","run":"<actions url>","utc":"…"}`, with the version **bare**
   (no `v`). A file and not a commit
   status, because a status is about a *teko commit* and the canary is about an *mc version*, and
   the mapping would have to be invented; a branch and not GitHub Pages, because it needs no Pages
   setup and is versioned by git. teko writes it with its own `GITHUB_TOKEN`; mc reads it with
   `curl` and no token at all.
3. **`promote` is a job, not a step**, for `publish-to-registry`'s exact reason
   (`release.yml:672`): a failed promotion must not be able to unmake a published release, and a
   rerun of the job alone is the retry. Manual promotion is one command,
   `gh release edit v0.17.0 --prerelease=false`, and the release note says so.
4. **Timeout 90 minutes** (`timeout-minutes: 95`), polling every 60 s. The budget: up to 15 minutes
   for teko's schedule to notice, plus its recipe, which on its own 2026-09-14 dry run was a
   `build`, 64 fixtures, a bootstrap fixed point, `check-docs` and `mc limits`. A `workflow_dispatch`
   on teko's side removes the 15.
5. **"Bloqueante no 1.0.0" is one repository variable.** Before 1.0.0 the `promote` job is
   `continue-on-error: true` and a timeout is a `::notice::` with the release promoted anyway --
   advisory, so a teko outage cannot hold an mc patch. At 1.0.0 `vars.MC_CANARY_REQUIRED` is set,
   `continue-on-error` becomes false and a timeout leaves the release a pre-release. Same shape as
   `MC_REGISTRY_PUBLISH` (§ 0), same reason: a job that is red by design would hide a real failure.

### 6.3 What the mc side owes and what it does not

It owes: the pre-release flag, the poll, the flip, `needs: promote` on the registry job, and a
`docs/ci.md` § The canary that states the contract precisely enough for teko to implement its half
without asking -- the URL shape, the JSON keys, the timeout, and that a missing file is neither
`ok` nor `fail`. It does **not** owe teko's workflow, which is teko's pull request, and it does not
owe a fallback: if teko never publishes a verdict, every release before 1.0.0 is promoted on the
timeout and the pipeline is exactly what it is today.

## 7. RC 0.17.0 and the version string -- decision (design question 5)

**0.17.0 is an ordinary minor tag. "RC" is a STATE of the repository, not a suffix on a version.**

Three reasons, all measured in § 1.3:

1. `scripts/next-version.sh:206` and `.github/workflows/tag.yml:52-56` refuse a suffix, each with
   its own error text, and `docs/ci.md` § Versioning records that as a decision with a reason.
   Relaxing two refusals for one tag is a change to the release automation with no second user.
2. A `-`-suffixed version is **skipped by the compiler's own resolver** (`pkg_newest`/`pkg_pick`
   with `pre = 0`), so `mc upgrade` and `mc pkg add mc` would not offer it. A release candidate
   nobody can install is not one.
3. The *candidate* semantics already have a home where they can be acted on: the GitHub release's
   **pre-release flag**, which § 6 flips on a verdict. That flag is orthogonal to the version
   string, which is what lets 0.17.0 be an ordinary version and still be a candidate.

So:

| | |
|---|---|
| **0.17.0** | an ordinary `release:minor` tag, cut by `autotag.yml` as any other. It contains the freeze gate, the inventory, the policy and the canary in advisory mode |
| **0.17.x** | **bug fixes only.** Nothing is added to the inventory and nothing is removed from it; `git log --stat -- tests/golden/surface.txt` between the two tags should be empty |
| **1.0.0** | a `release:major` tag. The only difference in the tree is `vars.MC_CANARY_REQUIRED` and the policy page's "promised" wording |

`scripts/set-version.sh` and `scripts/check-bundle.sh`'s sentinel are untouched: they already do the
right thing for a plain `X.Y.Z`, and this decision means no suffix ever reaches them.

## 11. Risks

1. **Freezing a name teko needs renamed.** Measured at low: teko registers `syntax_expr`, `machine`
   and `target` (§ 0), the owner stated on 2026-09-08 that the hooks API does not move again, and
   teko replied the same day that nothing pends. The escape is § 5.2's lane, which costs one MINOR
   and one alias and is exactly what the direction asks for. The residual is that a *bad* name gets
   one major of life -- which is the price of the promise and not a defect of it.
2. **The canary's latency.** Bounded at 90 minutes (§ 6.2.4) and advisory until 1.0.0, so the worst
   case before 1.0.0 is a release that takes an hour and a half to leave pre-release. After 1.0.0
   the worst case is a release that stays a pre-release until a person promotes it by hand, which
   is one command. A `workflow_dispatch` on teko's side is the fast path and should be documented
   in the release checklist.
3. **The inventory drifting with `check-docs`'s regex.** Closed by construction in § 4.1: there is
   one regex, in one file, read by both gates. The residual is that the regex itself is a *choice*
   about what is public (17 prefixes and now 8 exact names), and widening it later adds entries --
   an additive, re-recorded MINOR, which is the right cost for "we noticed something was public
   all along". § 1.2a is that event happening once, deliberately, before the freeze rather than
   after it.
4. **A public symbol outside the prefixes stays invisible.** The regex is a heuristic and always
   was. What makes this survivable is that the ONLY names a consumer may rely on are the ones
   `docs/reference/` documents, and `check-docs` requires a documented name to exist -- so a
   documented-and-frozen name cannot vanish, and an undocumented one was never promised. § 1.2a
   found the one case where those two sets had parted (three names documented as frozen and
   unextracted), and the fix makes the invariant "documented ⊆ inventory" true for the families the
   regex covers. A sweep of `docs/reference/` for call-shaped names outside the inventory is priced
   at ~20 lines of one-off `grep` and is worth running once in step A.
5. **A merge conflict in a 420-line sorted file.** Sorted by kind then name bytewise (§ 4.2), so two
   pull requests adding different symbols conflict only if the names are adjacent. Cheaper than any
   alternative and identical to what `mc.toml`'s `[package].files` already does.
6. **`--record` used as a reflex.** The gate's message is written to discourage it (§ 4.3 prints the
   policy sentence *before* the command), and the recorded diff is in the pull request where a
   reviewer sees a deleted line. There is no technical defence against a determined re-record, and
   there should not be: the goldens have the same property and it has held for fifty milestones.
7. **0.17.x taking a feature.** The gate cannot stop it -- an addition is a legal MINOR at any
   point. § 7's "bug fixes only" is a discipline, and the check is one command in the 1.0.0
   checklist: `git log --stat v0.17.0..HEAD -- tests/golden/surface.txt` must be empty.
8. **The verdict file's owner.** mc reads a URL in a repository it does not control. A compromised
   or mistaken teko could promote a bad mc release -- but only to `prerelease: false`, which is a
   *visibility* flag; nothing about the artefacts changes and `publish-to-registry` still runs its
   own sandboxed validation. The blast radius is "a release becomes visible early", which is
   today's behaviour for every release.
9. **Diagnostics left unfrozen** (§ 3b). A consumer that greps a message will break on a PATCH. The
   answer is written down in the policy rather than engineered around: exit codes are the contract,
   and `mc` has 373 messages precisely because it improves them.

## Implementation notes -- step C (the canary)

Written while landing § 6, § 8.6-8.8 and § 9 row 3. Every deviation from the text above is here.

1. **The verdict lives at the ROOT of the `canary` branch, and § 6.2 point 2 has been corrected in
   place.** The prose said "a file in a branch of teko's repository, `canary/<version>.json`" while
   the URL beside it read `raw.githubusercontent.com/<owner>/teko/canary/<version>.json`. Those are
   two different files: the raw URL is `<owner>/<repo>/<REF>/<path>`, so the branch already occupies
   the `canary` segment and a file inside a `canary/` directory would be
   `.../teko-lang/canary/canary/0.17.0.json`. The **URL** was right and the prose was wrong. The
   ROOT form is also what the consumer was told through the channel on 2026-09-14 and what it is
   building, so the spec's prose is now the URL's shape and § 6.1's diagram names the real
   repository.

2. **The consumer is `teko-org/teko-lang`**, read out of the channel file
   (`/Users/schivei/mc-teko/teko-to-mc.md`, 2026-09-14) and confirmed against `gh repo list
   teko-org` -- not guessed from the milestone's shorthand. It is the DEFAULT of `CANARY_REPO` in
   the script and not a literal in the workflow, with `vars.MC_CANARY_REPO` overriding it, so a move
   is one variable and no commit. Its `canary` branch does not exist yet (`gh api
   repos/teko-org/teko-lang/branches/canary` -> 404, and the raw URL answers 404), which is exactly
   the state the poll treats as "not written yet".

3. **Armed is `vars.MC_CANARY == 'true'`** (§ 6.2 point 1's own spelling), not `"1"` or
   `"required"`; `"required"` is a second variable, `MC_CANARY_REQUIRED`, because the two questions
   are independent -- a release can be born a pre-release and promoted advisorily long before the
   wait blocks. Same gating shape and same reason as `MC_REGISTRY_PUBLISH` (§ 0).

4. **The timeout promotes before 1.0.0**, per § 6.2 point 5 read literally: *"a timeout is a
   `::notice::` with the release promoted anyway -- advisory"*. It is a `::notice::` and not the
   `::warning::` the task's brief supposed; the spec is what the script follows. At 1.0.0
   (`MC_CANARY_REQUIRED = true`) the same timeout is an `::error::` and the release stays a
   pre-release.

5. **`continue-on-error` is an expression**, `${{ vars.MC_CANARY_REQUIRED != 'true' }}` -- so the
   two states of § 6.2 point 5 are one variable and not two workflow edits. A `fail` VERDICT is exit
   1 either way: `continue-on-error` keeps the RUN green before 1.0.0, but the job renders red,
   which is what § 8.7 asks of it.

6. **The poll is a script and not thirty lines of YAML.** `scripts/canary-poll.sh` (167 lines, 106
   of them neither comment nor blank) can be run off a runner, which is the only way § 8.6's round
   trip can be reasoned about before a real tag exists, and it is the repository's own precedent
   (`next-version.sh --test`, `libroot.sh`, `release-assets.sh`). `--test` is **7 assertions over
   `file://` URLs**, no network and no framework: `ok` promotes, a `v`-prefixed version field is
   accepted, `fail` exits 1 and says so, a verdict naming another version keeps waiting, an advisory
   timeout promotes with the `::notice::`, a required timeout is exit 1 with the `::error::`, and
   the derived URL is the one § 6.2 point 2 writes. `--url TAG` prints the URL without touching the
   network, which is how that last case avoids a live request. `DRY_RUN` prints the `gh release
   edit` it would run instead of running it.

7. **The registry job's `if` had to name a status function.** `needs: [publish, promote]` alone
   would skip `publish-to-registry` on every release while `MC_CANARY` is unset, because a job whose
   `needs` is SKIPPED is skipped too. It is
   `!cancelled() && vars.MC_REGISTRY_PUBLISH == 'true' && needs.publish.result == 'success' &&
   needs.promote.result != 'failure'`. The load-bearing half is unambiguous: at 1.0.0
   `continue-on-error` is false, a `fail` or a required timeout makes `needs.promote.result` equal
   `failure`, and the pre-release is not announced. Before 1.0.0 the advisory job's `result` is
   reported as `success` and the registry runs -- which is what "advisory" means, and it is
   documented rather than relied on silently.

8. **The release note says how to promote by hand**, and only while the canary is armed: `publish`'s
   body composer appends a Canary paragraph with `gh release edit <tag> --prerelease=false` when
   `vars.MC_CANARY` is `true`. Whoever finds a release still marked pre-release has the one command
   in front of them without reading `docs/ci.md`.

9. **Unarmed is byte for byte the pipeline that was there.** `publish`'s `case "$VERSION" in *-*)`
   is untouched and the new `if [ "$CANARY" = "true" ]` below it is the only addition; `promote` is
   skipped; the registry job's extra conditions are all true. Nothing in `src/`, `stage0/`,
   `tests/golden/` or `lib/` was touched -- `git diff --stat src/ stage0/ tests/golden/` is empty,
   no golden moves, and `mc` emits not one different byte.

10. **`actionlint` is clean.** The two findings it reports on `release.yml` (SC2155 at `:527`,
    SC2086 at `:547`) are byte for byte the ones it reports on the same file from `main`, in the
    same steps, and predate this change; `shellcheck -s sh scripts/canary-poll.sh` is clean.

11. **The four outcomes, from the lines.** `ok` -> `promote()` -> `gh release edit "$TAG"
    --prerelease=false`, exit 0, registry runs. `fail` -> `::error::`, the by-hand line, exit 1;
    advisory the run is green and the registry still runs, required the run is red and the registry
    is skipped. `timeout` -> advisory: `::notice::` + `promote()` + exit 0; required: `::error::` +
    exit 1, the release left a pre-release. `unarmed` -> `promote` skipped, the release created
    exactly as before, the registry gated on `MC_REGISTRY_PUBLISH` alone as it always was.

12. **What is NOT proved here and when it will be.** § 8.6 asks for the round trip measured once
    against a real teko run and § 8.8 for the job graph of a throwaway tag. Neither can be done from
    a pull request: `release.yml` fires on a `v*` tag, the owner cuts tags, and teko's `canary`
    branch does not exist yet. The first real round trip is the next tag with `MC_CANARY` armed --
    the elapsed time from `publish` finishing to `promote` flipping goes into these notes then, with
    the run URL.
