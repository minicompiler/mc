# Spec M49 -- the optimizer: `--opt`, a register allocator over the callee-saved half, a machine-private peephole, loop-invariant hoisting -- and the two roads

Written against `minicompiler/mc` `main` at `63e3e86` (M48 C2), read-only session, 2026-09-06, on the host `docs/comparison.md` measured (Apple M4, macOS 26.6.2, Apple clang 21.0.0). `docs/plan.md`'s M49 row is an ESTIMATE ("within 1.3x of `clang -O2`"); this spec replaces the estimate with measurements taken before anything was designed (§ 1), and every design decision below cites the number it rests on.

The one-paragraph version. The 2.2x gap is three separate gaps. `mix` (the LCG/xorshift loop) is 0.39 s of the 0.60 s, and it is the store-then-load chain through the frame -- every local read and written through `[sp, #k]` -- that a register allocator removes: hand-emitting what the walker plus an allocator would produce and timing it gives 0.63 s -> 0.38 s with registers alone, 0.28 s with the peephole on top, 0.26 s with the loop-invariant constants hoisted. `primes` is 0.13 s of the gap, half of it `clang -O2`'s NEON vectorisation of the count loop, which nothing here reaches; the allocator plus peephole gives 0.29 -> 0.21, hoisting 0.20. `fib` is 0.08 s of the gap and is NOT a codegen-quality gap: `mc`'s cost per call (1.42 ns) is already below clang's (1.58 ns); clang makes half as many calls because it turns the second recursive call into a loop. Registers buy 0.18 -> 0.17 there and nothing else in this milestone reaches the rest. The sum, 0.26 + 0.20 + 0.17 = **0.63 s against 0.49 s = 1.29x**, is what the design below is sized to deliver; without hoisting it is 0.66 s = 1.35x. And the peephole ALONE, on today's code, buys **nothing measurable** (0.66/0.30/0.19 against 0.63/0.29/0.18) -- the loops are latency-bound on the frame round trip, not on instruction count -- which inverts the order the plan row implied: the allocator lands first, the peephole after it.

## 0. What this stands on (read, not assumed)

* **The pipeline and its seams.** `cli.mc:322` / `driver.mc:413` / `limits.mc:589` run `run_passes(unit)` over the folded AST; every object backend calls `gen_lower(root)` (`backend_exe.mc:906`, `backend_elf.mc:543/551`, `backend_coff.mc:421/429`, `backend_elf_exe.mc:971/982`, `core_writers.mc:37`) and then `gen_encode_all()`; `--dump-asm` is `gen_lower` + `gen_dump_asm` (`cli.mc:329`). `gen_lower` = `gen_resolve` + `gen_sections` + `gen_globals` + one `gen_func` per function (`gen_walk.mc:1199-1209`); `gen_func` (`:1073-1113`) runs `MTASK_PROLOGUE`, one `MTASK_PARAM` per parameter, the body, `MTASK_LABEL(lepi)`, `MTASK_EPILOGUE`, `MTASK_FRAME_FIX(frame)`. The frame is `slot_new(size)` (`:392`), a positive offset the machine turns into `sp + (frame - off)` at the end (`fix_frame`, `machine_arm64.mc:300`). A local is `MTASK_LOCAL_LOAD/STORE(ty, d, off)` from `gen_ident`/`gen_assign`/`gen_var` (`:658-668`, `:883-892`, `:864-881`); `&x` is `MTASK_LOCAL_ADDR` and the resolver marks the DECLARING node (`res_addr_taken`, `gen_resolve.mc:248`, `res_addr` `:349-366`, keyed by node because sibling blocks reuse a local index).
* **Contract version 4** (`docs/reference/machine.md`): 31 slots in `MTASK_*` order (`gen_walk.mc:64-95`), depth indices never registers, `val_reg/dst_reg/dst_done` the only three machine internals a module may call (§ 3), `walk_depth_type`/`walk_ret_type` published as functions and explicitly NOT slots (the M24 precedent for "the walker answers a question without a slot"). A derived machine copies `MTASK_COUNT` entries out of `machine_tab("arm64")` and patches slots (`lib/machine_arm64_float.mc:661-692`, `lib/machine_probe.mc:121-126`, `lib/machine_x86_64_float.mc:755-772`); the two third-party machines fill a global `uptr m_rv64[MTASK_COUNT]` (`examples/kernel/machine_riscv64.mc:156`, 31 `rv_task` calls at `:791-`) and `examples/avr/machine_avr.mc` the same way -- a global array is zero-filled, so every slot they do not name is **0**. `mach(task)` (`gen_walk.mc:305`) reads the table with no null check.
* **The machine's spill and its liveness** (`src/machine_arm64.mc`): depths 0..6 in `x9..x15` (`REG_BASE 9`, `REG_MAX 6`), `x8` the remainder scratch, `x16/x17` spill scratch, `dslot[MAXDEPTH]` one frame slot per depth on demand; `save_live(d)`/`restore_live(d)` (`:245-260`) store/reload depths `0..d-1` around every `bl`/`blr`; `arg_to_reg` (`:262`) and `a64_stack_args` (`:283`) read a depth as `REG_BASE + d` when `in_reg(d)`. **`lib/machine_arm64_float.mc` does the same direct read in three places** (its own integer `fa_save_live`/`fa_restore_live` and the stack-argument path: `if (in_reg(d)) r = REG_BASE + d;`) instead of going through `val_reg` -- relevant to § 5.
* **The ABI contract** (`docs/reference/objects.md` § 4, asserted by `scripts/check-surface.sh:608-980`): `x0..x7` read and never written by the prologue; the epilogue is `add sp` (absent at frame 0), `ldp x29, x30, [sp], #16`, `ret` and leaves `x0` alone; the `stp x29, x30` frame record unconditional; `x18..x28` "never written, never read" -- measured today as **0 mentions in the 1745 functions of `src/mc.mc`** (`nhigh`, `check-surface.sh:966`), and **no file under `lib/` or `examples/` names `x19..x28`** (grep over `*.mc`/`*.lx`, 0 hits), so no runtime in this tree keeps state there today. `#opcode`/`emit()` words are emitted where they stand with nothing inserted (`objects.md` § "`#opcode` names registers"); `src/mc.mc`'s own dump has **0 `.word`** lines (its syscalls go through libSystem), `lib/sys_svc.mc` is where they live.
* **The seed constraint.** `stage0/` (2848/3000, frozen) has no optimizer. `scripts/check-obj.sh` compiles every `tests/*.mc` with `build/mc0` and `build/mc1` and `cmp`s the objects (32/32); `check-asm` diffs the two `--dump-asm`s over `tests/ lib/ src/`; `bootstrap.sh` is `mc0 -> mc1.o -> mc2.o -> mc3.o`, `cmp mc2.o mc3.o`, SHA-256 against `tests/golden/mc2.sha256` plus the four foreign goldens (`tests/golden/README.md`). None of these scripts passes a flag to the compiler, so an optimizer that is OFF without a flag leaves all of them untouched by construction.
* **The globals budget.** `build/mc1 limits src/mc.mc`: `globals 445 / 512` (86.9%); `check-limits` fails at 90% (460). Fifteen file-level globals of `src/gen_walk.mc` are read by NO other file (`pend_type pend_sym pend_node prel_base nloops lbreak lcont frame_off nlocals localcap loopcap prelcap nprel walk_fn_ret walk_ret`, plus `dtype`) -- measured with `grep -rlw` over `src lib examples`; the machines touch only `nins`, `ins_base`, `slot_new`, `MAXDEPTH` and the `e*` emitters.
* **The folder** (`src/parse.mc:1085-1176`): constant with constant only, guarded by kind (`fold_taught`); a `pass()` is `i64 f(root)` over the flat node array in registration order (`hooks.mc:62`, `run_passes` `:301`), `lib/pass_demo.mc` the worked example (`x * 1 -> x`, 29 lines).
* **The flag parser** (`src/cli.mc:188-240`): `str_eq(a, "--dump-asm")` for a mode, `opt_val(a, "--machine=")` for a valued flag, the last one wins; `scripts/check-docs.sh:107-125` enumerates every `"--[a-z][a-z-]*=?"` literal in `src/` and demands a `docs/reference/cli.md` row -- a bare `-O` would not be enumerated, `--opt=` would. `[project]` has four keys (`docs/reference/toml.md:61-70`, `drv_run` reads `kind` at `driver.mc:775`).
* **`I_BCOND` (`b.<cond>`) exists in the encoder (`machine_arm64.mc:730`), the dump (`:648`) and the surface encoder (`lib/backend_arm64.mc:128`) but is emitted by no task today** -- `MTASK_JZ/JNZ` lower as `cbz/cbnz` (`:507-508`). It is the ONE instruction form the peephole adds to the sweep.
* **43 of the 1745 functions of `src/mc.mc` execute a `callp`** (`blr x16` in the dump) -- the walker's `gen_*` family, every `run_passes`/`subcommand` dispatch.
* **`fib(38)` makes 126 491 971 calls** (`2 * fib(39) - 1`); clang's `-O2` `_fib` (21 instructions, one `bl` per loop iteration) makes about half.

What a register allocator removes and what a peephole removes, counted on the hot loops:

* `mix`'s loop body is **50 instructions per iteration**: 13 loads and 10 stores of the four locals `x acc i y` (every one a frame round trip -- `str x9, [sp]; ldr x9, [sp]` back to back, four times), 14 `movz/movk` re-materialising the two 64-bit constants (4 + 4), `ITERS` (2), the three shift counts and `1`; 8 ALU instructions; and a **five-instruction condition** `cmp; cset lt; cmp #0; cset eq; cbz` -- the `!(i < N)` the prelude's `while` expands to. `clang -O2`'s loop is 7 instructions (`madd`, three `eor` with a shifted operand, `add`, `subs`, `b.ne`), constants hoisted.
* `primes`' sieve inner loop is 20 per iteration (4 loads/stores of `j` and `i`, `adrp/add` of `sieve` re-materialised every time, `N` re-materialised, the same 5-instruction condition); the count loop 27. clang's inner loop is 7 with four `strb` (unrolled), and the count loop is NEON (`cmeq.16b`, 16 bytes per `ldp q`).
* `fib`: 7 `mov`s, 5 loads and 2 stores of `n` and the first result, for 2 `bl`. clang keeps `n` in `x20`, the running sum in `x19`, and loops.

### 1.2 What each technique buys -- hand-emitted from today's dump, assembled, timed

Each variant is today's `--dump-asm` text with ONE transformation applied by hand, exactly the instructions the walker plus that mechanism would emit (no clang, no other change), assembled with `clang -O0 x.s` and timed the same way. Scratchpad files `mixA.s mixB.s mixC.s mixD.s primesB.s primesC.s fibA.s todayP3.s`.

| variant | what changed | `mix` | `primes` | `fib` |
|---|---|---|---|---|
| today | -- | 0.63 | 0.29 | 0.18 |
| **P** peephole only (`cset/cmp/cset/cbz` -> `b.cond`, 191 -> 176 instructions) | on today's code | 0.66 | 0.30 | 0.19 |
| **A** allocator only: locals in `x19..x22`, every `ldr/str [sp]` a `mov` to/from the register, everything else as today (50 -> 50 per iteration, no memory) | | **0.38** | -- | **0.17** |
| **B** = A + peephole (`b.cond` fusion; `mov x19, x9; mov x9, x19` collapsed; the ALU result written straight into the local's register) -- 28 per iteration | | **0.28** | **0.21** | -- |
| **C** = B + immediate operands (`lsr #13`, `add #1`) -- 24 per iteration | | 0.28 | -- | -- |
| **D** = B + loop-invariant hoisting (the two 64-bit constants and `ITERS` in `x23..x25`; `sieve`'s address and `N` in `x22/x23`) -- 18 per iteration | | **0.26** | **0.20** | -- |
| `clang -O2` | | 0.24 | 0.16 | 0.10 |
| `clang -O1 -fno-vectorize -fno-unroll-loops -fno-inline` (an upper bound: registers + hoisting + shifted operands + fib-to-loop) | | 0.24 | 0.18 | 0.07 |

Read:

1. **The allocator is the lever: 0.25 s of `mix`'s 0.39 s gap** (A), and the remaining instruction-count reductions only pay once the frame round trip is gone: P alone is noise, B on top of A is another 0.10 s. The M4 is wide enough to absorb 50 instructions per iteration; what it cannot absorb is `str` -> `ldr` forwarding on the loop-carried `x`.
2. **Immediate operands buy nothing** (C = B). Not in scope.
3. **Hoisting buys 0.02 + 0.01 s** (D) and is what takes the projected sum from 1.35x to 1.29x. In scope, last.
4. **`fib`'s floor is 0.17 s.** Per call `mc` already spends less than clang (0.18 s / 126.5M = 1.42 ns; clang 0.10 s / ~63.2M = 1.58 ns); the gap is the call count, i.e. the recursion-to-loop rewrite clang applies to the second call, which is outside this milestone. Small-leaf inlining does not apply (the function is recursive).
5. **`primes`' floor without vectorisation is about 0.20 s** (D); `clang -O2`'s 0.16 is the NEON count loop and the 4x-unrolled inner loop, neither in scope.

Projected with A + B + D: **0.26 + 0.20 + 0.17 = 0.63 s, 1.29x of 0.49 s** (§ 9 makes 1.3x the acceptance, with the per-phase numbers as the diagnostic when it misses). Without D: 0.66 s, 1.35x.

### 1.3 The cost side, before designing

* The allocator's pre-pass is one linear walk over each function's nodes -- the same order and cost as `res_func`, which already walks them (`gen_resolve.mc:588`); over `src/mc.mc` that is 173 542 nodes. The peephole is emission-time pattern matching on the last one or two `Ins` records, not a pass. Neither allocates proportional to anything but the function. Bound for § 9: self-compile with `--opt=1` under **+30%** over the plain road (0.95 s -> under 1.24 s), target +10%.
* Code size: each allocated register costs one `str` in the prologue and one `ldr` before the epilogue; `--dump-asm` of `bench.mc` will grow by about 2 per allocated register per function and shrink by the removed frame traffic. `src/mc.mc`'s `__text` is 461 420 B today; bound **+5%**.

## 2. Where it lives -- decision (design question 1)

| road | what it can express | measured gain on the workload | price (lines of `src/`) | decision |
|---|---|---|---|---|
| (a) an `Ins`-level pass between `gen_lower` and `gen_encode_all` | machine-specific patterns over `I_*` -- which the WALKER may not read (the `I_*` vocabulary is the machine's, `machine.md` § 2 "the walker owns `I_LABEL` and nothing else") | alone: 0 (variant P); with (b): 0.10 s on `mix` | ~120 in `machine_arm64.mc` | **yes, but machine-private and at emission time**, not a pass and not a slot: the machine asks `walk_opt()` (§ 6) |
| (b) walker-level register allocation of locals over the callee-saved registers | what the resolver and the walker already know: which declarations are locals, which have their address taken, how often and how deep each is used; the machine knows which registers are callee-saved | 0.25 s (`mix`), 0.08 s (`primes`, with the peephole), 0.01 s (`fib`) | ~260 walker + ~120 arm64 + ~110 x86-64 | **yes -- the milestone** |
| (b') loop-invariant constants and symbol addresses as pseudo-locals of the same allocator | | 0.03 s | ~80 walker | **yes, last** (§ 4.8) |
| (c1) AST-level constant propagation (`pass()`) | `x = 5; y = x + 1` -> `y = 6`; nothing in the workload has that shape (its constants are already literals `fold` handles) | 0 measurable | ~150 | **deferred**; priced, no consumer measured |
| (c2) AST-level small-leaf inlining (`pass()`) | copy a leaf body at the call, params to gensym locals, `return` -> assign + `break N` out of a wrapping `loop` | 0 on the workload (no small leaf in a hot path; `ld8/st8` are intrinsics, `fib` is recursive); self-compile: the accessors (`nd_kind`, `ld64`) are the obvious win, unmeasured | ~300 | **deferred** to a follow-up with its own measurement on `src/mc.mc` |

The allocator goes in the walker because the walker is the only place that knows liveness by construction -- it hands out depths and frees them, it drops a block's locals at the closing brace, it sees `res_addr_taken` -- and because `docs/comparison.md` § Where to improve and the plan row both named that seam. The machine keeps what is the machine's: WHICH registers are callee-saved, how many, how to move a depth into one and back, and how to save and restore them; and the copy propagation that makes an allocated register usable as an operand directly (the difference between A and B) is register knowledge and stays inside the machine (§ 4.6).

## 3. The switch, the seed and the two roads (design question 2)

### 3.1 The switch

* **`--opt=N`** on the single-file CLI and on `mc build`, `N` in {0, 1}; **`-O`** is an alias for `--opt=1` (parsed as its own `str_eq`, documented by hand in `cli.md` since `check-docs` enumerates only `--` literals). **`[project].opt = 0|1`** in `mc.toml` for a project (`docs/reference/toml.md` § `[project]`, fifth row); the flag wins over the key, the last flag wins over an earlier one, like every flag in `cli.mc`. The `--dump-*` modes honour it (`--dump-asm --opt=1` shows the optimized lowering; `--dump-machine` shows the v5 slots).
* **Default 0**, on every road, and it stays 0 when `stage0/` is retired: the unoptimized road is the reference every determinism gate compares against (`check-obj`, `check-asm`, the five goldens, `check-inert`, `check-surface`), and a reference must not move when the optimizer improves. A project that wants the speed says so once in its `mc.toml`. (D14 asks the owner to ratify the "stays 0" half.)
* Where the value lives: NOT a new global (§ 4.9) -- one field of the walker's record, read through `walk_opt()`, set by `cli.mc`/`driver.mc` through `set_walk_opt(n)` before `gen_lower` (the same place `--machine=` is applied).

### 3.2 The seed gates do not move

`check-obj` (32/32 against `build/mc0`), `check-asm`, `check-lex`, `check-ast` and `bootstrap` never pass a flag, and the optimizer with `walk_opt() == 0` runs no pre-pass, issues no v5 task and matches no pattern (the guards are `if (walk_opt() == 0) return` at the four entry points, § 4.2, § 4.4, § 6). Inertness is therefore by construction, and it is proved the M17 way anyway: `scripts/check-inert.sh build/mc1.pre build/mc1` before each commit lands (§ 7).

The plain golden `tests/golden/mc2.sha256` moves with every commit of this milestone -- the compiler's own body changes -- and is rewritten only after the empty `--dump-asm` diff between `mc1` and `mc2` and `cmp build/mc2.o build/mc3.o`, as always. It does NOT move because instruction selection changed for any program, which `check-inert` is what says.

### 3.3 The second golden, and the cross-road identity

`scripts/bootstrap.sh` gains a second chain after the first (skipped with a message when the compiler refuses `--opt=`, so the seed and any pre-M49 release still run stage 1-3):

```
build/mc1  --opt=1 src/mc.mc -o build/mc2o.o     (+ link -> build/mc2o)
build/mc2o --opt=1 src/mc.mc -o build/mc3o.o
cmp build/mc2o.o build/mc3o.o                    <- the optimized road's fixed point
sha256 build/mc2o.o == tests/golden/mc2-opt.sha256
build/mc2o          src/mc.mc -o build/mc2o-plain.o
cmp build/mc2o-plain.o build/mc2.o               <- the cross-road identity
```

The last line is the strongest correctness statement this milestone can make and it costs one compile: **an optimized compiler computes exactly the compiler the unoptimized one computes.** A miscompiled allocator that changes any decision anywhere in the 1745 functions of `src/mc.mc` shows up here as a byte difference, with `diff <(mc2 --dump-asm src/mc.mc) <(mc2o --dump-asm src/mc.mc)` as the bisection tool (`docs/determinism.md` § Fixed-point diagnosis applies unchanged). The foreign goldens (`mc2-linux-*`, `mc2-windows-*`) get their `-opt` twins when D2 lands (§ 10); until then `--opt=1` on an x86-64 machine is a no-op by the null-slot rule (§ 5) and the arm64 Linux/Windows twins are recorded in D1's commit.

### 3.4 `check-inert` on both roads

`scripts/check-inert.sh PRE POST` runs its `one`/`taught` loops a second time with `--opt=1` appended whenever BOTH compilers accept `--opt=0` (probe: `"$c" --opt=0 --host`), reporting `ok 33 objects identical (--opt=1)`. Across a change that touches the optimizer, the plain road must be identical and the optimized road is expected to differ only for the programs the change targets -- the script prints the list, and the commit message says which and why (the M45 discipline: "the diff is exactly these two instructions").

## 4. The allocator, in the walker

### 4.1 What is a candidate

A declaration -- `N_PARAM`, or a scalar `N_VAR` (`nd_val == 0`, no array) -- whose type has kind `TK_INT` or `TK_SINT` and width 8 or less (`uptr` included: a pointer is the machine's word; `i32`/`u8` included: the register holds the extended eight bytes, the slot invariant of `machine.md` § The AVR implementation), whose declaring node is not `res_addr_taken`, in a function that contains **no `RK_OPCODE` call and no `emit()`/`reloc()`** (the resolver already classifies every call; the pre-pass sets a per-function flag on the first one it meets and stops). Excluded by kind: `TK_FLOAT`, `TK_WIDE`, `TK_OPAQUE` locals stay in memory, so `<float>`'s machines never see a v5 task for a value of theirs.

**`callp` does not exclude a function.** AAPCS64, System V and Win64 all make `x19..x28` / `rbx r12..r15` the CALLEE's to preserve; the pointer target of a `callp` is an ordinary function that keeps that promise whether it was written in `mc`, in C, or in a `#opcode` body -- and a `#opcode` body that writes `x19` already breaks every C caller it has, with or without this milestone. Excluding the 43 `callp` functions of `src/mc.mc` would exclude the walker's own `gen_*` family, the hottest code in the compiler, for a risk the ABI already assigns to the callee. The owner may prefer the stricter rule (D5); it is one line in the pre-pass.

### 4.2 The pre-pass: `opt_scan(f)`, before `MTASK_PROLOGUE`

One walk over the function's body, in node order, carrying the loop nesting depth (`N_LOOP` increments on entry, decrements on exit). For every candidate declaration it counts weighted uses: each `N_IDENT` bound to it (`res_kind == RK_LOCAL`, `res_decl` matched against the declaring node's index AT THAT POINT -- the walk replays the same push/pop of block scope `res_func` did, which is what `res_local_slot` already relies on), each `N_ASSIGN` to it, and its own initialiser, at weight `8^depth` capped at `8^3`. Scores are integers, candidates are kept in **declaration order** in a per-function arena list (`opt` record, § 4.9), and selection is "repeat `n` times: take the highest score not yet taken, first in declaration order on a tie" -- no `qsort`, no hashing, stable by construction (`docs/determinism.md` rule 1 and 2). A candidate is taken only if its score is **at least 3** (a parameter read once costs a `mov` in, a `str`/`ldr` pair around, and buys nothing). `n` is the machine's answer to `MTASK_REG_COUNT` (§ 5), 0 when the slot is null.

The result is written into the resolver's side table: `RES_SIZE 32 -> 40`, a fifth field `RES_REG` on the DECLARING node (0 = none, `r + 1` otherwise). `res_tab` is allocated from `nnodes` and zeroed, and nothing outside `gen_resolve.mc` knows its stride.

### 4.3 What the walker emits

`gen_func`, with `walk_opt() != 0` and at least one allocated register (`opt_nreg > 0`):

```
MTASK_PROLOGUE
for each parameter i, in order:
    allocated to r  -> MTASK_PARAM_REG(ty, i, r)              // x(19+r) = x_i, x0..x7 only READ
    otherwise       -> slot_new + MTASK_PARAM(ty, i, off)     // as today
for each allocated r, in order:  off = slot_new(8); MTASK_REG_SAVE(r, off)   // the save area is ordinary frame slots
for each hoisted value (§ 4.8):  MTASK_CONST(0, v) / MTASK_SYM_ADDR(0, sym); MTASK_REG_STORE(TY_I64, 0, r)
body:
    gen_ident on an allocated local   -> MTASK_REG_LOAD(d, r)             // instead of LOCAL_LOAD
    gen_assign / gen_var initialiser  -> MTASK_REG_STORE(ty, d, r)        // instead of LOCAL_STORE; truncates to the width, extends by the kind
    N_CALL / N_RETURN / everything else unchanged
MTASK_LABEL(lepi)
for each allocated r, in REVERSE order: MTASK_REG_RESTORE(r, off)        // loads only; x0 untouched
MTASK_EPILOGUE
MTASK_FRAME_FIX(frame)
```

Why the save area is frame slots and not `stp x19, x20, [sp, #-16]!` pairs: the frame record stays `stp x29, x30; mov x29, sp; sub sp` and the epilogue stays `add sp; ldp x29, x30; ret` -- **every ABI assertion of `objects.md` § 4 holds verbatim on the optimized road too**, the saves are plain `str/ldr` forms every encoder already has (no new instruction in the sweep for them, no change to `lib/backend_arm64.mc`), `fix_frame` addresses them like any slot, and a debugger (M30) finds them at a fixed `[sp, #k]`. The cost is one instruction per register instead of one per pair, which § 1.3's size bound covers.

The `Local` record gets a fifth field, `LOC_REG` (`LOC_SIZE 32 -> 40`, -1 = not allocated), written by `set_loc_reg` right after `local_add` at the two sites; `local_add`'s signature does not move (it is a lowering function `objects.md` § 3 lists). `gen_ident`/`gen_assign` test `loc_reg(e) >= 0` before the existing branches, so the plain road's two calls are byte-identical text.

### 4.4 Inertness of the walker half, by construction

`opt_scan` returns immediately when `walk_opt() == 0`; `opt_nreg` is then 0; every branch above tests `loc_reg(e) >= 0`, which is never true because nothing set it. No slot is called, no `slot_new` is issued, no node is touched. That is what `check-inert` confirms and what `lib/machine_probe.mc` will assert (§ 7).

### 4.5 Narrow types in a register

`MTASK_REG_STORE(ty, d, r)` is "the value at `d`, truncated to `type_width(ty)` and extended by `type_kind(ty)`, into `r`" -- the machine emits `mov` then `gen_cast(x(19+r), ty)` for widths 1, 2, 4 (`and #0xff`, `sxth`, `mov w, w`...), nothing more for 8. Today `u8 x = 300` is `strb` (truncation in memory) then `ldrb` (zero-extension on the way back); the register version performs the same two steps at the store and none at the load, so `x == 44` on both roads. `MTASK_REG_LOAD(d, r)` carries no type: the register already holds the extended eight bytes, exactly as a spill slot does.

### 4.6 The arm64 machine: `x19..x28`, the alias table, the store rewrite

* `a64_reg_count()` answers **10**: `x19..x28`, `r -> x(19 + r)`. **`x18` is never allocated** (Apple's platform register; and the contract sentence "x18 never" stays unconditional).
* `a64_reg_save(r, off)` = `str x(19+r), [REG_FRAME, -off]`; `a64_reg_restore` the `ldr`; `a64_param_reg(ty, i, r)` = `mov x(19+r), x_i` for `i < 8`, `ldr x(19+r), [x29, #16 + 8*(i-8)]` above (the `MTASK_PARAM` rule, reading and never writing an argument register), then `gen_cast` for a narrow `ty`.
* **The alias table** is what turns variant A (0.38) into B (0.28) and it is entirely the machine's: `i64 dalias[MAXDEPTH]`, -1 by default, reset in `a64_prologue`. `a64_reg_load(d, r)` emits **nothing** and sets `dalias[d] = 19 + r`; `val_reg(d, scratch)` answers `dalias[d]` when it is set; every writer of a depth -- `dst_reg`/`dst_done`, `a64_const`, `a64_un` (in place: it first materialises `mov x9, x19` through `val_reg` and then clears the alias, since the result must not land in the local's register), `a64_cast`, `a64_load`, a call's result -- clears it; `save_live`/`restore_live`/`arg_to_reg`/`a64_stack_args` go through `val_reg` and skip the frame round trip for an aliased depth (the value is in a callee-saved register, the callee preserves it). The invariant: **a depth's alias is set only by `REG_LOAD` and only while that depth holds exactly the local's value; the local's register is written only by `REG_STORE`, which is a STATEMENT and therefore runs when depth 0 is the only live depth and every alias is stale by definition.** `a64_reg_store` clears all aliases after it writes.
* **The store rewrite**: `a64_reg_store(ty, 0, r)` looks at the last `Ins`; if it is an ALU/load/`cset`/`mov` whose `rd` is `x9` (the value it is about to move) and no label sits between, it retargets that `rd` to `x(19+r)` and emits no `mov`. That is what makes `x = x * C + K` end in `add x19, x9, x10` and `i = i + 1` in `add x21, x21, x10`. A `mov x9, xN` retargeted becomes `mov x19, xN`; a `mov x9, x19` (the depth reading the same local) becomes nothing.
* With `walk_opt() == 0` no `REG_LOAD` ever runs, so `dalias` is all -1 and `val_reg` takes its old branch on every call -- the bytes cannot move, and `lib/machine_probe.mc` asserts `dalias[d] == -1` for every depth after every task on the plain road.

### 4.7 The x86-64 machines (D2)

`rbx r12 r13 r14 r15` -> **5**; the same `x86_reg_*` functions serve `x86_64-win` through the copied table, so Win64 answers 5 as well and leaves `rdi`/`rsi` alone (they are argument registers 1 and 2 on System V; a count that depended on which prologue last ran would be stale for the first function of a unit, and two registers are not worth a second code path -- D11). Saves are `mov [rbp-k], rbx` (`X_ST64`), the alias table and the store rewrite are the same logic over `x86_desc` forms. No new x86 instruction form: `jcc` already exists for... it does not -- `x86_jz` emits `test; jz`; the peephole's `cmp; setcc; test; jz` -> `cmp; jcc` needs the `jcc rel32` row, one `x86_desc` line, added to the sweep like `b.cond`.

### 4.8 Hoisting: loop-invariant constants and symbol addresses as pseudo-locals (step C)

Inside a loop (nesting depth >= 1), two kinds of node re-materialise the same value on every iteration: an `N_INT` whose `gen_imm` needs two or more instructions (any 16-bit part above the low one non-zero -- `ITERS`, `N`, the two LCG constants), and the address of a global array, a string literal or `&global` (`adrp` + `add`). `opt_scan` records each distinct value (constants by value, symbols by symbol index, in first-occurrence order) as a candidate with the same weighted score as a local and the same threshold; a taken one gets a register after the locals, is materialised **once at function entry** after the saves (`MTASK_CONST`/`MTASK_SYM_ADDR` at depth 0 + `MTASK_REG_STORE`), and its uses become `MTASK_REG_LOAD`. Entry materialisation runs even when the loop is never entered -- a few instructions, never a fault (a symbol address is a relocation, not a load). Measured: `mix` 0.28 -> 0.26, `primes` 0.21 -> 0.20; it is the step that makes 1.3x from 1.35x.

### 4.9 State: arena records, zero net globals

The optimizer's state is one arena record, `opt` (per-function candidate list and its count, `opt_nreg`, the flag the pre-pass sets, the hoist list), allocated on first use like `drv_state`/`sb_state`, with accessors -- ONE file-level global for the pointer. It is paid for twice over by the walker diet this milestone carries as its step A: `pend_type pend_sym pend_node prel_base` (the four `reloc()`-pending fields nobody outside `gen_walk.mc` reads, measured § 0) move into a `wk` record behind one pointer, net **-3**; the flag `walk_opt()` reads is a field of `wk`. Result: **445 -> 443** on the seed's globals row, measured by `build/mc1 limits src/mc.mc` before and after, `check-limits` at 17/17. The diet is byte-identical by nature and is proved by `check-inert` in the same commit (the M48 C0 precedent, "twelve globals became one").

## 5. Contract version 5 (design question 3)

Version 4 -> 5 **appends six slots and changes no signature**; the version's second obligation is a rule about null slots, its third a sentence about `val_reg`.

| slot | signature | meaning |
|---|---|---|
| `MTASK_REG_COUNT` (31) | `i64 f()` | how many callee-saved registers this machine lets the walker allocate; **0 = none, and a NULL slot reads as 0** |
| `MTASK_REG_LOAD` (32) | `void f(i64 d, i64 r)` | depth `d` = the value in allocatable register `r` (`0 .. count-1`) |
| `MTASK_REG_STORE` (33) | `void f(i64 ty, i64 d, i64 r)` | register `r` = depth `d`, truncated to `type_width(ty)` and extended by `type_kind(ty)` |
| `MTASK_REG_SAVE` (34) | `void f(i64 r, i64 off)` | write register `r` into the frame slot at `off` (prologue side, after the parameters) |
| `MTASK_REG_RESTORE` (35) | `void f(i64 r, i64 off)` | read it back (epilogue side, before `MTASK_EPILOGUE`; must not touch the result register) |
| `MTASK_PARAM_REG` (36) | `void f(i64 ty, i64 i, i64 r)` | argument `i` straight into register `r`, extended by kind; argument registers are read, never written |

`MTASK_COUNT 31 -> 37`; `mtask_names[]` gains the six names; `--dump-machine` prints `-` for a null slot where it prints `bundled`/`taught`.

**The null-slot rule.** `mach(task)` stays as it is for slots 0..30 (a missing one is a bug in the machine and dies as today); for slots 31..36 the walker reads the entry itself and treats 0 as "the machine does not do this": `REG_COUNT` answers 0 and the other five are never called. That is the "0 = no allocatable registers" road, and it is what keeps **`examples/kernel/machine_riscv64.mc` and `examples/avr/machine_avr.mc` byte-identical with `--opt=1` and without, with no edit** -- their tables are zero-filled globals of `MTASK_COUNT` entries and they fill 31 (§ 0). A machine that wants the allocator fills the six; `riscv64` has `s1..s11` and could, in a later commit of its own.

**The derived machines.** `lib/machine_arm64_float.mc`, `lib/machine_x86_64_float.mc` and `lib/machine_probe.mc` copy `MTASK_COUNT` entries out of the bundled table and therefore inherit the six slots -- integer locals get allocated in a `<float>` program exactly as in any other, and float locals never reach a v5 task (§ 4.1). **What they must honour is the third obligation:** since version 5, when `in_reg(d)` is true the value of depth `d` may live in a register other than `REG_BASE + d`; a derived machine reads a depth through `val_reg(d, scratch)` -- the function version 3 published for exactly this -- and never computes `REG_BASE + d` itself. `lib/machine_arm64_float.mc` does that computation in three lines today (§ 0); D1 fixes them (its `fa_save_live`/`fa_restore_live` become calls to the bundled pair through `fa_of`, and the stack-argument path uses `val_reg`), and `check-float` with `--opt=1` on all its legs is the proof. Nothing else in `lib/` or `examples/` names a depth register.

**The ABI assertions** (`docs/reference/objects.md` § 4 and `scripts/check-surface.sh`):

* the nine `abi_case`s and the `src/mc.mc` sweep run on the plain road exactly as today, and the text "`x18..x28` never written" becomes: **`x18` is never written or read; `x19..x28` are never written or read on the plain road, and with `--opt=1` a function writes `x19+r` only after saving it and restores it before its epilogue, so a caller never sees them change** -- the C promise. A tenth assertion runs `--dump-asm --opt=1 src/mc.mc` and checks, per function, that the set of `x19..x28` mentioned in the body is a subset of the set stored right after the prologue's parameter stores and loaded right before `add sp` (an `awk` over the dump, same shape as `badpro`/`okret`);
* "a taught runtime may keep state in `x19..x28` across generated code" is **withdrawn** for programs built with `--opt=1` and kept for the plain road; `objects.md` says which. No runtime in this tree relies on it (§ 0), and the two float machines use `v16..v23`.

## 6. The peephole -- machine-private, emission-time, `walk_opt()`-gated

Not a slot and not a pass: the machine already sees the last instruction it emitted, and the four patterns below are all "the instruction I am about to emit consumes the one just emitted and nothing else can". Each is guarded by `walk_opt() != 0` -- published in `machine.md` § 3 beside `walk_depth_type`, the same "a function, not a slot" shape -- and by "no `I_LABEL` between" (a label means another path arrives).

| | pattern | rewrite | where | forms added |
|---|---|---|---|---|
| P1 | `cmp; cset rd, cc` then `MTASK_JZ(d, L)` with `rd == val_reg(d)` | drop the `cset`, emit `b.!cc L` (`JNZ`: `b.cc L`) | `a64_jz`/`a64_jnz` | **`b.<cond>`** (`I_BCOND`, encoded, dumped and in `lib/backend_arm64.mc` already; never emitted before) |
| P2 | `cset rd, cc` then `MTASK_UN(MUN_LNOT, d)` on the same `rd` | flip `cc` in place, emit nothing | `a64_un` | none |
| P3 | the alias table (§ 4.6): `MTASK_REG_LOAD` emits nothing | | `a64_reg_load`, `val_reg` | none |
| P4 | the store rewrite (§ 4.6): an ALU result then `MTASK_REG_STORE` | retarget `rd` | `a64_reg_store` | none |

P1 + P2 together turn the prelude's five-instruction `while` condition into `cmp; b.ge`. The `cset`'s register is dead after a `JZ`/`JNZ` in every walker site (`gen_if` at depth 0, `gen_logic` overwrites the depth on both paths), so P1 needs no liveness beyond adjacency. A peephole here only deletes, rewrites in place, or replaces `cset + cbz` by one branch; it never reorders across a label or a call and never introduces a form the sweep has not seen (P1's `b.cond` is the one addition, swept in D1's commit).

Measured: P1 + P2 alone, 0; on top of the allocator, 0.10 s on `mix` and part of `primes`' 0.08 s. Landing order follows the measurement (§ 10).

## 12. Risks (design question 7)

1. **Seed parity.** Guarded by construction (no flag, no code path) and by `check-inert` at every commit; the one way to break it is a refactor that moves a plain-road byte -- the walker diet of step A is exactly that kind of change and lands FIRST, alone, so its inertness is proved on its own.
2. **Third-party machines.** `riscv64`/`avr` are covered by the null-slot rule and `cmp`-identical images (§ 9.7). The float machines inherit the slots and MUST read depths through `val_reg` (§ 5); the three-line fix is in-tree, but a machine derived from `arm64` OUTSIDE this tree that computes `REG_BASE + d` would read a stale `x9` under `--opt=1` -- said plainly in `machine.md` v5 and in the release note. The plain road is unaffected either way.
3. **Debugging (M30).** A register-resident local has no frame slot; DWARF needs `DW_OP_reg19` for it and `DW_OP_fbreg` for the saved copy of the register in the prologue. `LOC_REG` is exactly the information M30's writer needs, and the fixed `[sp, #k]` save area keeps a stack walker's view unchanged. M30's spec should read this section.
4. **The `#opcode`/`emit()` escape.** Functions with either are never allocated; the residual risk is a `#opcode` body CALLED from an allocated function that writes `x19..x28` -- a body that already breaks every C caller. `objects.md` says so; `lib/sys_svc.mc`'s words name `x16` and `x0..x2` only (checked).
5. **Code size** grows by two instructions per allocated register per function and shrinks by the removed frame traffic; § 9.9's 5% bound on `src/mc.mc` is the check, and `--dump-asm --opt=1 bench.mc`'s count is recorded.
6. **Determinism.** No hashing, declaration and first-occurrence order, an integer score, a stable "take the max" loop; the twice-compiled `cmp` and the fixed point on the optimized road are the gates.
7. **The alias table's correctness** is the milestone's real risk: a stale alias reads the wrong register with no diagnostic. Three independent nets: the probe's invariant on every task over `src/mc.mc`, `check-opt`'s run-equality over 60 programs and the four examples, and the cross-road identity over the 1745 functions of the compiler itself.
8. **Self-compile time**: bounded at +30% (§ 9.3); the pre-pass is linear and the peephole is O(1) per instruction.
9. **Globals**: net -2 (§ 4.9), measured at every commit.
10. **Two roads in the diagnosis recipe** (`docs/determinism.md`): one added paragraph; the cross-road identity says which road to bisect.
11. **Win64 `rdi/rsi`** left unallocated (D11): a measured decision can revisit it when M50's x86-64 cell exists.
12. **Runtimes keeping state in `x19..x28`**: none in the tree today (grep, § 0); the contract sentence is withdrawn for `--opt=1` only.
13. **`check-surface`'s hard-coded prologue/epilogue expectations** hold on both roads by the save-area design (§ 4.3); the tenth assertion covers what changes.
14. **The 1.3x itself**: a projection from hand-emitted code, 1.29x with C and 1.35x without; the host's run-to-run spread is about 5% on these three binaries (§ 1.1's three runs). If D1 + B land at 1.35x, C is what closes it; if C lands and the ratio is still above 1.3x, § 9.2's per-phase numbers say where, and the next measured lever is `mix`'s shifted-operand `eor` (variant D's loop is 18 instructions against clang's 7, latency-bound at the `mul`/`add` chain either way).

## 13. Decisions (architect) -- to ratify with the owner

* **D1 -- `--opt=N`, `-O`, `[project].opt`, default 0.** Recommend yes. Not `-O2`/`-O3` levels (one road to test, not three), not an environment variable (determinism: the flag is in the command line or the manifest, nowhere else).
* **D2 -- the allocator in the walker, the peephole machine-private at emission time, no `Ins` pass.** Recommend yes (§ 2): the walker owns liveness, the machine owns registers, and a pass over `I_*` would put machine vocabulary in the walker.
* **D3 -- contract version 5: six appended slots, the null-slot rule for slots 31+, `walk_opt()` as a function.** Recommend yes; the alternative (a v5 machine MUST fill the six) would force an edit on `riscv64` and `avr` for a feature they do not use.
* **D4 -- arm64 allocates `x19..x28` (10), never `x18`.** Recommend yes; a smaller set (`x19..x26`, leaving two for a runtime) is one constant, if the owner wants the "runtime state" sentence kept for `--opt=1` too.
* **D5 -- `callp` does not exclude a function from allocation; `#opcode`/`emit()`/`reloc()` do.** Recommend yes (§ 4.1). The stricter rule is one line.
* **D6 -- landing order A, D1, B, C, D2; E deferred.** Recommend yes: measured (§ 1.2), the peephole alone is nothing.
* **D7 -- the second golden AND the cross-road identity as gates.** Recommend yes; the identity is the cheapest strong proof available and costs one compile per bootstrap.
* **D8 -- zero net new globals through the walker diet (`pend_*`, `prel_base` into `wk`).** Recommend yes; alternative: the fifteen private walker globals into `wk` at once (-14), a bigger inert refactor for the same proof.
* **D9 -- hoisting (step C) in scope.** Recommend yes: it is what reaches 1.3x, 80 lines, one test.
* **D10 -- inlining and constant propagation deferred**, with their own spec measured on `src/mc.mc`. Recommend yes.
* **D11 -- Win64 allocates the same five registers as System V.** Recommend yes until measured otherwise.
* **D12 -- the acceptance number is 1.3x on THIS host with the three phases recorded**, and M50's cell becomes the reference when it exists. Recommend yes.
* **D13 -- the `Local` record and the side table grow by one field each (`LOC_SIZE 40`, `RES_SIZE 40`).** Recommend yes; both are internal, no accessor's signature moves.
* **D14 -- `--opt` stays off by default after `stage0/` is retired.** Recommend yes: the plain road is the determinism reference and the seed for every foreign chain; a project opts in with one key. To revisit only with a measurement that the optimized road has been the fixed point of every release for a version series.
